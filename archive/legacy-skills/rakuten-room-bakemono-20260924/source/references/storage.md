# ローカル保存・データ管理の仕様（このスキルの土台）

このスキルは「続けるほど精度が上がる」ことが価値。そのために設計・候補・履歴をローカルに保存し、毎回読み込んで使う。**ファイル操作を間違えるとユーザーの資産が壊れる**ので、この仕様に厳密に従うこと。

## 1. 保存先

**保存先は、Codexで開いている作業フォルダ内の `rakuten-room/`。**

例：ユーザーがデスクトップに `楽天Room BAKEMONO` という作業フォルダを作ってCodexで開いた場合、保存先は次になる。

```text
<作業フォルダ>/rakuten-room/
```

Windows例：

```text
C:\Users\<ユーザー名>\Desktop\楽天Room BAKEMONO\rakuten-room\
```

重要：

- 旧仕様の `~/rakuten-room/` は使わない。配布ユーザーごとに作業フォルダ内へ保存する。
- スキル本体は `<作業フォルダ>/.agents/skills/` に置く。ユーザーデータは `<作業フォルダ>/rakuten-room/` に置く。
- `.agents/skills/` の中にユーザーデータを保存しない。スキル更新時に混ざるため。
- shellを使う場合は、実行前に現在の作業フォルダを確認し、`./rakuten-room/` を必要に応じて絶対パスへ解決してから読む/書く。
- もしカレントディレクトリが `.agents/skills/<スキル名>` の中になっている場合は、`.agents` の親フォルダを作業フォルダとして扱う。
- ユーザーが別の場所を明示した場合だけ従い、その旨を `account.md` の先頭に記録する。
- 探索先は選択中の作業フォルダ内だけ。ホームや別プロジェクトの旧データは自動探索・読み込み・移行提案をしない。ユーザーが移行元を明示して引き継ぎを指示した場合だけ、その指示に従う。

構成：

```text
<作業フォルダ>/rakuten-room/
├── account.md       # アカウント設計（このROOMの憲法。最重要）
├── products.md      # 固定候補リスト（10〜15商品のローテーション元）
├── post-drafts.md   # 投稿文の作り置き（商品ごとの完成文。プランはここから選ぶ）
├── posts-log.md     # 投稿ログ（計画→実績→反応）
├── schedule.md      # 投稿時間方針・スケジュール済みタスク設定・セール日程メモ
├── archive/         # 肥大化したログの退避先（必要になったら作る）
│
│  ── ここから下はカレンダー連携したときだけ作られる（オプトイン）──
├── calendar.json    # Supabase接続情報（URL・publishable・secret）。secretを含むので公開厳禁
├── drafts/          # 日付ごとの投稿文（YYYY-MM-DD.md。同期・カレンダー表示用）
├── calendar-web/    # 公開用の index.html + config.js（無料ホストに上げる）
└── .image-cache.json # 商品og:imageのキャッシュ（再取得を避ける）
```

**カレンダー連携は完全にオプション。** `calendar.json` が無ければ従来運用（Supabaseに触れない）。連携の手順は `references/calendar-setup.md`、同期は `references/calendar-sync.md`。

## 2. 起動時（毎回・最優先で実行）

1. 現在Codexで開いている作業フォルダを確認する。
2. 作業フォルダ内の `rakuten-room/` の存在を確認する。
3. **無ければ** → 同じ作業フォルダ内に `rakuten-room/` を生成し、初回セットアップへ進む。別の保存先は探さない。
4. **有れば** → 存在する運用Markdown（`account.md` `products.md` `post-drafts.md` `posts-log.md` `schedule.md`）を読む。空フォルダや未作成ファイルは破損扱いにしない。
5. `account.md` が無ければ初回セットアップへ。設計済みなら、候補が未作成の場合はSTEP Cから、候補もある場合は前回プランの反応確認から再開する。必要なファイルが無ければ該当工程で `assets/templates/` の雛形から生成する。アカウント設計・商品・実績を推測で埋めず、既存ファイルは維持する。
6. 存在するファイルが壊れている/読めない場合は、勝手に作り直さず、原因を伝えて復旧方法を確認する。

### 診断・実行テストの途中から再開する場合

- ユーザーが「最初から」「URLをもらった後から」など再開地点を指定した場合は、その地点を優先する。やり直しはデータ削除の指示とは扱わない。
- 診断途中でも公開情報の観測結果・本人回答・未回答項目・次の工程を作業フォルダ内のMarkdownに保存する。例：`room-observation-<ROOM ID>.md` と `room-diagnosis-<ROOM ID>.md`。既存記録があれば更新・追記する。
- `account.md` が未作成でも、会話や作業フォルダ内の診断記録にURLと回答があればそこから再開する。初回質問へ自動的に戻さず、未確認の項目だけ聞く。
- 「適当」という投稿量・選定方法の回答はそのまま保存し、定量値や具体的な選定元を補わない。売上0とクリック未確認も区別する。
- 新規ルートの設計案や過去のテスト用データを、別の既存ROOMの確定方針として流用しない。今回のROOM URL・観測事実・本人が確定した方針を対応付けて保存する。
- ルーチンの登録状態は会話やファイルだけで断定せず、必要時に登録先で確認する。ファイルがないことを未登録の証拠にせず、重複作成を避ける。

## 3. 前回プランの反応確認（重複防止）

`posts-log.md` は、プランを作った後に次回起動で反応を確認するためにも使う。

### 確認対象

次の条件をすべて満たす直近行だけを確認対象にする。

- 日付が今日より前、または今日の投稿予定時刻を過ぎている投稿計画
- `実施` が `計画` または `実施済み`
- `反応メモ` が空欄、`－`、`不明`、`未確認` のいずれか
- `反応メモ` に `確認依頼済み` が入っていない

該当行が複数ある場合は、直近1日分だけ聞く。古い未確認行を何日分もまとめて質問しない。今日の予定時刻前の投稿は、まだ結果確認しない。

### 聞き方

確認対象があれば、今日の投稿プランに入る前に次のように聞く。

```text
前回の投稿、クリックや反応はありましたか？
「クリック3件」「反応なし」「まだ見てません」だけで大丈夫です。
```

聞いた直後に、対象行の `反応メモ` を `確認依頼済み（YYYY-MM-DD）` に更新する。これが「一度聞いた」印になる。

### 二重に聞かないルール

- `反応メモ` に `確認依頼済み` がある行は、次回以降もう聞かない。
- `クリック3件` `反応なし` `売上1件` `未確認（回答 YYYY-MM-DD）` など、ユーザーの回答が記録済みの行も聞かない。
- ユーザーがあとから「前回はクリック5件だった」と自分から伝えた場合だけ、その行を更新する。
- `確認依頼済み` は傾向分析の反応データとして数えない。傾向分析に使うのは、クリック数・売上・反応なしなど、実際の回答だけ。

### 回答をもらった後

ユーザーの返答を次のように分類して、対象行の `実施` `反応メモ` `判定` `学び` を更新する。

- `クリック3件` `売れた` `いいねあり` など → `実施済み`、反応ありとして記録
- `反応なし` `別に` `何もない` など → `実施済み`、反応なしとして記録
- `まだ見てません` `未確認` など → `実施済み` または `計画` のまま、`未確認（回答 YYYY-MM-DD）` と記録
- 投稿していない場合 → `見送り` とし、理由を `反応メモ` または `学び` に記録

記録後に、今日の投稿プランへ進む。

投稿を実施した事実と実際の投稿日が確認できた場合だけ、`products.md` の最終投稿日を更新する。予定日を実施日とみなさず、日付不明なら未確認と記録する。未投稿・結果未確認を購入ゼロとして判定しない。

## 4. 書き込みのルール（厳守）

- **追記が原則。既存の記録を消さない。** 特に `posts-log.md` の過去行は書き換えない。ただし、前回プランの反応確認では、対象行の `実施` `反応メモ` `判定` `学び` だけ更新してよい。
- 書き換えるのは `account.md` の設計内容（見直し時）と `products.md` の候補（入れ替え時）のみ。その際も**変更履歴を残す**（account.mdの更新履歴セクション／products.mdは外した商品を「入れ替え履歴」に1行残す）。
- 全ファイルの先頭で `最終更新：YYYY-MM-DD` を必ず更新する。
- 日付は**絶対日付**（YYYY-MM-DD）で書く。「昨日」「先週」は使わない。
- 実データのみ。確認できていない価格・クーポン・セール日程は書かない（確度ラベルの ✅🔍💭 を残してよい）。
- 保存後は「保存しました」と一言＋更新した項目を1行で伝える（何が積み上がったかをユーザーに見せる）。
- セッションの最後（プラン確定後）は**必ず**該当ファイルを更新してから締める。

## 5. 各ファイルの仕様

雛形は `assets/templates/` にある。初回作成時はこれをコピーして埋める。

### account.md（ROOMの憲法）
- ここが全判断の基準。毎回必ず読み、これに反する商品・投稿文は提案しない。
- ジャンルを変えたい相談が来たら即書き換えず、「ジャンル変更は評価の一貫性を壊す」旨を伝えた上で判断（`methodology.md` 参照）。変更する場合は更新履歴に理由付きで記録。
- ルートBの診断結果もここに蓄積する（診断履歴セクション）。2回目以降の診断で「前回の指摘が直っているか」を照合できる。

### products.md（固定候補リスト）
表の列と記入ルール：

| 列 | 記入ルール |
|---|---|
| 優先度 | 加熱スコアのA（最優先）／B（テスト候補）。C（今回は見送り）は候補に入れない |
| 商品名 | 実ページで確認した正式名（長ければ識別できる範囲で短縮可） |
| URL | 実ページのURL。**確認していないURLは絶対に書かない** |
| 価格 | 確認時点の価格。変動前提 |
| 刺さる悩み | account.mdのターゲットの悩みと紐づく1行 |
| 確定役割 | 入口／関連／収益拡張／予告 から**1つ**。この役割の完成文を post-drafts.md に作る |
| 加熱スコア | 6項目の合計と内訳。未確認は分母から除く（methodology.md §6） |
| 加熱根拠 | 6項目のどれで加熱と判断したか＋クーポン期限（あれば） |
| 確認日 | 実ページを見た日 |
| 最終投稿日 | この商品を最後に投稿した日（未投稿なら空欄） |

運用ルール：
- 毎日の選定は**このリスト内のローテーション**。リストにない商品を思いつきで出さない。
- **再投稿の判定**：`最終投稿日` から1〜2週間経っていれば、切り口を変えて再投稿可。1週間未満は出さない。
- 計画を作っただけでは最終投稿日を更新しない。予定の重複は `posts-log.md` の同日・同商品・同役割の計画行で確認し、同じ計画は追記し直さない。確認日は実ページを確認できた日だけ更新する。
- **鮮度管理**：`確認日` が7日以上前の商品は、本命にする前に実ページを再確認する（加熱が続いているか・クーポン期限）。
- 候補がA級不足（3件未満）または全体が枯れてきたら再リサーチを提案。入れ替えた商品は「入れ替え履歴」に理由付きで1行残す。

### post-drafts.md（投稿文の作り置き）
- リサーチ（STEP C）で候補ごとに書く、**そのまま貼れる完成投稿文**。1商品＝`## <商品名>` セクション。商品名は `products.md` と一致させる。
- 各セクションに `products.md` の商品IDを記入する。日次報告と投稿文の見出しはそのIDから始め、商品名・商品URLと照合する。管理用IDはコピー用本文に入れない。
- 各セクションの中身：**役割（1つ）／確認日／コンプラ✅／完成文（冒頭40〜45字→本文→次行動導線→ハッシュタグ）**。
- **プラン（STEP D）は、ここから該当商品を取り出し、その日の時事だけ微調整**して使う。ゼロから書かない。
- 役割を変える・切り口を変える時は、その商品のセクションを書き換える（1商品1文を保つ）。
- 作り置きが無い商品をプランで使ったら、その場で作って**ここに追記**する（次回から使い回せる）。

### posts-log.md（投稿ログ）
- **計画→実績→反応**の3段階で育てる。プラン提示時に「計画」行を追記し、次回起動時に実施状況と反応を埋める。
- 「商品」列は `P12 アミュード スープ4種` のように `products.md` のIDを先頭に付ける。日次報告・完成文の見出しも同じIDで照合する。
- **1日に複数投稿する日**は、その日付の行を投稿ごとに複数行書く（日付が同じ行が2〜3行並んでよい）。
- 反応メモは数字を優先（クリック数・いいね・売上件数）。ユーザーが反応なしと答えた場合のみ「反応なし」と書く。数字不明は「未確認」とし、購入の有無が不明ならBと決めず判定を保留する。
- 一度質問しただけで未回答のものは `確認依頼済み（YYYY-MM-DD）` と書く。これは重複質問を避けるための印であり、良い反応として扱わない。
- 「学び」列に、その投稿から分かった構造の知見を1行（例：「意外性型の冒頭がクリック伸びた」）。**この蓄積が横展開の判断材料**になる。
- **「判定」列にA/B/Cを入れる**（反応を聞けた行だけ。未確認の行は空欄のまま）：

| 判定 | 条件 | 次にやること |
|---|---|---|
| **A（伸ばす）** | 購入・売上につながった | **売れた商品ではなく「売れた条件」を残す**（ターゲット属性・価格帯・役割/文章型・投稿時刻・ジャンル）。同条件の周辺商品を3件再検索して候補に足す |
| **B（修正する）** | クリックやいいねは出たが購入に至らなかった | 原因候補（価格帯／比較不足／商品ページとのズレ／購入理由が弱い）から**1つだけ**選んで直す。価格違いの比較を足す・訴求を変える・投稿順序を変えるのいずれか |
| **C（撤退する）** | 反応がほぼ無い | 同じ商品を粘らない。その条件の優先度を下げ、別の周辺需要へ移す。`products.md` の入れ替え履歴に理由を書く |

- 軽量モードではA判定後も新規開拓しない。周辺商品3件の補充は次回の手動リサーチに引き継ぎ、未実施として記録する。手動時に探した商品も加熱スコアと選定条件を満たすものだけ候補へ追加する。
- 判定を書いたら、Aで抜き出した「売れた条件」を下の「効いているパターン」にも必ず反映する。**商品名ではなく条件を蓄積する**のがこのファイルの目的。
- 投稿数が100行を超えたら、古い分を `archive/posts-log-YYYY.md` に退避し、本体には直近30〜50件を残す（直近30投稿が評価の中心のため、それ以上は本体に不要）。

### schedule.md
- 投稿時間の方針（黄金時間のどこを使うか）
- スケジュール済みタスク設定の有無・時刻・登録先（ローカルスケジュール済みタスク／スケジュールタスク）
- 直近の確定セール日程メモ（**確認日と確度ラベル付き**。💭推定は推定と明記）。日付が過ぎたものは削除してよい

## 6. 学習ループ（保存データの使い方）

保存は目的ではなく、**次のプランを良くするため**にある。毎回のプラン作成時に必ず参照する：

1. `posts-log.md` の「判定」列と「学び」列 → **A判定の条件を今日のプランに優先的に再利用し、B判定は直す点を1つだけ引き継ぎ、C判定の条件は今日の候補から外す**
2. `posts-log.md` の「効いているパターン」 → 蓄積された勝ち条件（ジャンル・価格帯・文章型・時間帯・ターゲット）を今日の絞り込み条件に使う。運用日数が増えるほど、市場だけでなく**自分のROOMの実績**を条件に加える
3. `posts-log.md` の直近の役割の並び → 今日の役割を決める（入口→関連→収益拡張の流れを壊さない）
4. `products.md` の最終投稿日 → 再投稿可否とローテーション
5. `account.md` の診断履歴 → 前回指摘した弱点が直っているかを確認し、直っていなければ再度そこを最優先にする

反応データが3件以上たまったら、プランの冒頭で**傾向を1行フィードバック**する（例：「これまでの5投稿だと、問題提起型の冒頭が一番クリックされています」）。これが「続けるほど当たる」実感になる。

## 7. やってはいけないこと

- ユーザーの記録を確認なしに削除・上書きする
- 実ページを見ていない商品情報・URLを書く
- 「反応不明」「確認依頼済み」を良い反応として扱う（分からないものは分からないと書く）
- 回答済み・確認依頼済みの前回プランについて、毎回同じ質問を繰り返す
- ファイルが無いのに有るふりをして、記憶や推測でプランを作る（無ければ初回セットアップに戻す）
- ログをスキルの内部メモとして使う（**ユーザーが自分で読んで分かる日本語**で書く。将来ユーザーが他ツールに移っても資産として残る形にする）
- **Astraのノート機能（長期記憶）だけを根拠に前日の判断を語る。** 引き継ぎの正はこの `rakuten-room/*.md`。ノートは補助で、設定や環境によっては残らない。ファイルに書いていないことは「記録がない」と言う
- **ユーザーのアカウントにログインする／ID・パスワード・ワンタイムコードを求める。** 反応データ（クリック・購入・売上）はユーザーから受け取り、公開ページの読み取りだけで済ませる
- 加熱スコアの見られなかった項目を0点や推測で埋める（`未確認` と書いて分母を下げる）

## Mission③の日次工程の記録

`daily-operation-YYYY-MM-DD.md` に進行中の工程・調査根拠・候補判定・次に受け取る指示を保存する。日次運用の再開時に参照し、完成済みの工程を重複実行しない。工程と誘導は `daily-loop.md` に従う。閲覧・クリック・いいね・購入は期間と情報源を添えてposts-log.mdに記録し、未確認は数値0に変換しない。
