# ローカル調査ブリーフ

商品ページにはアクセスせず、既存の商品台帳・投稿ログ・このフォルダーのJSON設定だけを使って、未投稿在庫と次の調査量を集計する。

```powershell
npm run research:brief
npm run research:brief -- --date 2026-09-23
npm run research:brief -- --format json
```

標準出力に短い調査ブリーフを表示する。JSON形式は、後続のローカル処理へ渡す場合に使う。台帳やログは書き換えない。

## API一括候補収集

```powershell
npm run research:collect
```

ローカル調査ブリーフで不足しているジャンルを優先順に選び、`search-queries.json` の検索語で楽天商品検索APIを呼ぶ。各検索の間を最低1,200ミリ秒空け、商品コードまたはクエリ・末尾スラッシュを除いた商品URLで重複を統合する。`products.md` の商品URLと `posts-log.md` の「実施済み」IDを照合し、商品台帳の最終投稿日も投稿済みとして扱う。計画中・台帳登録済みも新規候補とは分けて保存する。

結果は `api-results/api-results-<UTC timestamp>.json` に保存する。検索元キーワード、ジャンル、API結果、照合状態を含む。途中のAPI検索が失敗しても取得済み結果を保存し、失敗件数を報告する。全検索が終わっても `products.md` や `posts-log.md` へは自動登録しない。採用・商品ページ確認後に候補を確定する。

`search-queries.json` は不足ジャンルごとの検索語・取得件数・APIリクエスト間隔を設定するファイル。楽天ジャンルIDを推測せず、キーワードを編集して使う。

`genre-plan.json` は5ジャンルの日次投稿数・在庫目標、確認期限、ページ調査単位、採用率の仮置きを持つ。採用率40%は小さな初回調査の実績から置いた作業量の目安にすぎず、予測値ではない。

`genre-map.json` は商品IDごとのジャンルを明示する。商品台帳に新しい商品を追加したら、実際に確認したジャンルをここへ追加する。未設定のIDは在庫に算入されず、ブリーフに要確認として出る。

投稿ログの「実施」欄が「実施済み」のIDだけを投稿済みとして除外する。「計画」は除外しない。確認日から7日以上経った商品、確認日のない商品、重複URLの商品は有効在庫へ数えず、再確認対象として表示する。URLの比較ではクエリとフラグメントを取り除く。

調査優先順は、在庫数を日次投稿数で割った在庫日数が少ないジャンルを先にし、同じ場合は日次投稿数の多いジャンルを先にする。調査ページ数は不足件数を仮採用率で割った目安であり、実際の採用数に合わせて更新する。

楽天公式APIの商品検索・ランキング取得は[API利用手順](../../scripts/README-rakuten-api.md)を参照。取得した商品は自動で台帳に登録されない。
