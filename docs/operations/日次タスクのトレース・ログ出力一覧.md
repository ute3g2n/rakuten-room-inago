# 日次タスクのトレース・ログ出力一覧

確認日：2026-10-19 JST

実装照合時のGit HEAD：`d7241547d5e6111962177105c9149d6414a2ddee`（U23.08 working-tree diffを照合）

対象：現在の `RakutenRoomInagoDaily`（production）の起動から、検索・AI生成・成果収集・HTML出力・保全まで。投稿報告の受付・オフライン取込・翌日反映も、日次とつながる記録として含めます。

日次タスクは、検索語句を調べ、ROOMで候補商品を探し、紹介文の下書きを作り、成果を集計して結果を保存します。その途中経過と結果は、一つのログへ集約されているわけではありません。工程の共通トレース、AI専用ログ、ブラウザーの観測ファイル、SQLiteの処理履歴に分かれています。本書は、**各出力がどこに、いつ、どの形式で保存され、何と照合できるか**をまとめた現行実装の一覧です。

ソースコードと保存先の構成を読み取り、Windowsのタスク履歴チャネル設定をread-onlyで確認して作成しました。日次の起動、再試行、投稿、設定変更、DB変更は行っていません。個別ファイルは、その工程を実行した場合だけ作られます。本書にある保存先のすべてが、現時点で作成済みという意味ではありません。

## 1. 保存先の基準とファイル名

本書では、次の略称を使います。

| 略称 | 現在の基準ディレクトリ | 用途 |
| --- | --- | --- |
| `R` | `C:\project\rakuten-room-inago` | リポジトリ |
| `D` | `R\rakuten-room-inago\runtime` | 本番の日次状態・ログ・観測ファイル |
| `B` | `R\rakuten-room-inago\backups` | 本番バックアップ・隔離復元確認 |
| `C` | `<user_profile_root>\.codex` | AI実行に使うCodex home。現在のユーザープロファイル配下 |

`D`と`B`はproduction設定の読み込み時に検証されます。たとえば `D\logs` は、現在の環境では `C:\project\rakuten-room-inago\rakuten-room-inago\runtime\logs` です。

- `<run_id>`：対象実行のID。通常は `INAGO-YYYY-MM-DD`。
- `<target_date>`：実行が対象とする日。`YYYY-MM-DD`。
- `<job_id>`：AIへの一つの依頼。`attempt`はその依頼の試行番号。
- `<request_id>`：Google Trendsの取得依頼。ROOMでは検索の `<attempt_id>` が共通トレース上の `request_id` になります。
- `<offer_key>`：商品の識別キー。下書きと生成ログを結び付けます。
- `<action_id>`：本人の投稿・見送り・訂正・編集報告を、ブラウザーから管理反映まで追うID。
- `<encoded_…>`：PythonのURLエンコードを通した値です。たとえばID中の `:` はファイル名では `%3A` になります。ログ内のIDとファイル名が完全に同じ文字列とは限りません。
- JSONは一ファイルに一つの文書、JSONLは一行に一つのJSONオブジェクトです。独自に保存するJSON/JSONLはUTF-8です。`.response`はAI最終応答の生バイト列を保つ拡張子で、壊れたJSONや空応答もあり得ます。

根拠：[productionのパス・構成](../../automation/inago/production_runtime.py)、[起動用ラッパー](../../automation/inago/run.ps1)、[日次タスク定義](../../automation/inago/task-xml/RakutenRoomInagoDaily.xml)。

**出力される時点に違いがあります。** `daily_pipeline` の外側工程は、処理中はメモリーに時刻付きtimelineを蓄積し、export・保全の処理後にL02へまとめて追記します。検索workerの詳細stageも、Pythonがworker結果とstderrを回収してからL02へ移します。したがって、ファイル末尾の追記順は必ずしも発生時刻順ではなく、強制終了時にはまだ保存されていない工程があります。実行中の進捗はS02とS01も併せて確認します。

## 4. CLIの結果ログ（L01、X01）

出力実装：[cli.py `_append_production_log`・`_run_production`・`_emit`](../../automation/inago/cli.py)。

### 4.1 `production-cli.jsonl`

一行の基本形は `at`、`mode`、`status` です。必要な場合だけ `reason`、`phase`、`diagnostics` を付けます。`at`はUTCのISO 8601です。改行区切りで追記し、flushとfsyncを行います。

日次の `diagnostics` には次の情報を記録します。

- `overall_status`、`daily_status`、`daily_reason`、`reason`。
- `committed_count`、`shortfall_count`、`source_failures`、`error_count`。
- `primary_error`、`secondary_errors`、`phase_results`。
- `dashboard_export_status`、`daily_runs`、`draft_count`、exportの `error_code`・`file_name`。
- `preservation_status`、`end_backup_status`／`end_backup_error`、`monthly_restore_status`。

起動前確認で止まった場合は、`mode=daily`、`status=blocked`、`reason=startup_preflight_blocked`、`phase=preflight` と、失敗したcheck名を保存します。ブラウザープロファイルについては、存在や期待パスとの一致をbooleanで残し、プロファイル内容は残しません。

ただし、保存先rootを安全に確定できない、root自体がない、書込みができない場合はL01にも記録できません。その場合は標準出力・標準エラーだけになる経路があります。

このファイルはCLIの全出力をコピーするものではありません。通常日次では最後に結果を追記するため、それより前の強制終了で最終行がないことがあります。また、setup・export・backup・restore-check・serveのCLI記録も同じファイルに入るので、`mode`で絞ります。`status`やread-only recoveryの結果は標準出力へ返す経路があり、すべてがこのファイルへ記録されるわけではありません。

### 4.2 標準出力と標準エラー

CLIは詳細な結果オブジェクトを標準出力へJSON一行で返します。L01より詳しい `pipeline_trace`、工程別結果、保全先などを含む場合があります。例外時の `runtime_error`、ログ保存失敗時の `log_unavailable` は標準エラーへJSONで返します。

日次XMLはPythonを直接起動し、`run.ps1`もPythonの終了コードを渡すだけです。**現行の起動定義には、stdout/stderrを `stdout.log` や `stderr.log` へ保存するリダイレクトがありません。** 手動起動の呼出し元が保存しなければ、これらのstreamが後からファイルで読めるとは限りません。

Pythonのwarning（AIログの書込失敗など）はPython loggingにも渡しますが、専用FileHandlerや共通のファイル設定はありません。標準の警告出力とL01を混同しないでください。保持適用の `daily_retention_applied` はINFOと `extra` で発行していますが、現行CLIがINFOをファイルへ保存する設定はありません。

## 5. 全工程共通トレース（L02）

出力実装：[trace.py](../../automation/inago/trace.py)、[daily_pipeline.py](../../automation/inago/daily_pipeline.py)、[live_sources.py](../../automation/inago/live_sources.py)、[ai_runner.py](../../automation/inago/ai_runner.py)、[report_trace.py](../../automation/inago/report_trace.py)。

### 5.1 保存単位・日付・記録される工程

`D\logs\traces\<日付>\<run_id>.jsonl` へ複数componentが追記します。共通schema versionは整数 `1` です。

| component | 主なoperation／意味 | 保存先の日付・書込時点 |
| --- | --- | --- |
| `daily_pipeline` | `preflight`、`database_open`、`prepare`、`start_backup`、`operations_monitor`、`daily`、`operations_monitor_stop`、`database_close`、`export`、`preservation` | 日次結果の対象日。外側工程のtimelineを最後にまとめて保存。run IDがなければ `not_written` |
| `orchestrator` | `retention` | proposed runの対象日。保持処理の実行時に記録 |
| `public_source` | `trends_request`、`room_request`、ブラウザーの各stage、失敗・取消・後片付け | **source開始時点の実際のJST日付**。開始の後、詳細はworker回収後に追加 |
| `ai_runner` | `ai_job`。専用AIログの安全な開始・終了状態を反映 | AI依頼の `target_date`。AI lifecycleとともに追記 |
| `human_api` | `report_receipt` | 下書きが属するrunの対象日。受付のbeginと成功後end |
| `report_import` | `report_import` | 取込を実行した日次runの対象日。batch commit後にactionごとのend |
| `report_apply` | `report_apply` | 反映を実行する日次runの対象日。actionごとのbegin／end／error |

日次が午前0時をまたいだ場合、`public_source`だけが翌日フォルダーへ出力され、同じrun IDの他componentと保存先が分かれることがあります。`<target_date>`の一フォルダーだけを調べず、`logs\traces`全体から同じrun IDのファイルを探します。これは現行コードの出力先の違いで、日次全体の17:45・18:00終了期限はありません。

Trendsでは検索画面、検索入力、期間変更、関連ワード欄の更新・待機を追えます。ROOMでは条件画面の開閉、検索一覧、商品ごとの確認、詳細クリック、別画面／同一画面の移動、元一覧への復帰、取得上限・終了判断を追えます。たとえば `trends_period_reflected` の次に `trends_top_rows_wait_begin` で止まれば、期間選択後の関連ワード表示待ちまで進んだことを示します。これだけでGoogle側の根本原因が分かるわけではありません。

### 5.2 一行のschema

必須項目は次のとおりです。

| 項目 | 意味 |
| --- | --- |
| `schema_version`、`event_id` | 共通schema版、イベント固有UUID |
| `span_id`、任意の `parent_span_id` | 同じ一連の操作と親操作を結ぶID |
| `component`、`operation`、`phase` | どの処理が何をしたか。phaseは `begin/end/error/cancel/status` |
| `at`、`elapsed_ms` | 発生時刻（JSTのoffset付きISO 8601）、経過ミリ秒 |
| `run_id`、`target_date` | 実行と、このwriterへ渡された対象日 |
| `correlation_status` | 関連付けが `complete/partial/unresolved` のどれか |
| `retention_expires_at` | 当該イベントのraw保持期限 |

| ROOMの操作対象 | `element_tag`、`element_role`、`element_visible`、`element_enabled`、`element_obscured`、`handler_kind`、`handler_tag`、`handler_scope`、`has_href`、`href_kind`、`link_target`、`link_scope` |
| ROOMの移動・走査 | `destination_kind`、`timeout_ms`、`wait_elapsed_ms`、`row_failure_count`、`identified_row_count`、`stable_round`、`row_status`、`end_evidence` |

自由文、画面本文、投稿本文、URL、検索語、認証値、例外messageはallowlistの対象外です。**共通schemaに `evidence_ref` や `artifact_ref` はありません。** 証拠へ進む際は、同じrequest/job IDの観測ファイルやSQLiteの参照を使います。観測JSONやTFAILには共通トレースへの `trace_ref` が入ります。

### 5.3 容量と書込失敗

- writerが扱う一runファイルあたり最大2,048イベント、4 MiB。イベント一件は最大16 KiB。
- `logs\traces`配下のJSONLにファイル数上限は設けない。
- 上限時は `trace_suppressed` のmarkerを残し、状態を `degraded` にします。抑止のため1,024 bytesを予約します。
- 書込不能は `unavailable`。一部だけ追記された場合は、そのwriterの追加書込みを止めます。正常記録へ読み替えません。
- `D\logs\traces\.quota.lock` は件数・容量・保持処理の排他用ファイルで、イベントログではありません。
- 共通トレースが書けなくても、commit済みの下書きや本人報告をrollbackする用途には使いません。処理の正本はSQLiteです。

### 5.4 日次障害の安全な捕捉（U23.08）

`daily_pipeline`の失敗eventと`daily_pipeline_failure`の構造化logは、pipeline内の同じ例外捕捉位置を示す`failure_module`/`failure_function`/`failure_line`/`code_sha256`を共有します。この位置はcallback内部の例外発生箇所や根本原因ではありません。hashを読めない場合は欠測/nullとして扱い、別の版を推測しません。`error_name`は既知SQLite enum、`constraint_label`は`unique/primary_key/not_null/check/foreign_key/unknown`、`processing_label`は`run_create/daily_pipeline`、`table_label`は`run/unknown`に限定します。提案run IDと永続化済みrun IDを分け、永続IDなしはJSONLにnullで保存します。

failure logはrollbackとfailure resultの組立後にbest-effortで出し、`daily_pipeline_trace_result`も同様に例外を隔離します。logger handlerまたはtrace writerの失敗は日次結果を置き換えず、rollbackを妨げません。loggerの可視性・保存先は実際に設定されたhandlerに依存します。例外本文、traceback本文、SQL、params、絶対path、URL/query、投稿本文、資格情報、秘密、個人情報は出しません。

## 6. AI・紹介文生成の専用ログ（L03～L05、A02～A03、W01、X02）

### 6.1 AI一依頼・一試行のログ（L03）

出力実装：[ai_runner.py `_trace_path`・`_trace_event`](../../automation/inago/ai_runner.py)。

基本項目は文字列版 `schema_version="1"`、`at`（JST）、`event`、`run_id`、`job_id`、`attempt`、`task_id`、`settings_version`。認証方式、process状態・終了値、結果と採否、error code、実モデル・reasoning設定、artifact参照、所要時間、観測したCLI event種別、専門子一覧、JSONL妥当性、spawn数、sandbox設定を許可項目として追加します。プロンプトや生成本文、CLIのstdout/stderr全文はこのログへ転記しません。

発行するeventは `job_started`、`auth_observed`、`cli_started`、`cli_event`、`cli_finished`、`artifact_saved`、`session_trace_observed`、`job_finished` です。日次は一つのapp-server rootを複数job/turnで使うため、`cli_*`というevent名だけから「商品ごとに別CLIを起動した」とは判断しません。`job_finished`、SQLite `ai_job`、応答artifactを照合します。

### 6.2 日次AI rootの通信ログ（L04）

出力実装：[daily_ai.py](../../automation/inago/daily_ai.py)、[app_server.py `_log`](../../automation/inago/app_server.py)。

JSONLの各行は `event`、`at`（Unix秒の数値）と、許可された `method`、`thread_id`、`turn_id`、`process_pid`、`status`、`returncode`、`code` からなります。`process_started`、`rpc_sent`、`rpc_failed`、`request_denied`、`root_ready`、`turn_started`、`turn_finished`、`job_transport_failed`、`interrupt_sent`、`process_closed` を記録します。

このファイル名はrunごとではなく日付ごとです。各行に `run_id`や`job_id`が必ずある形式ではないため、L03、`run.checkpoint.ai_daily_root.root_thread_id`、turn時刻と合わせて追います。JSON-RPCの本文や応答全文は記録せず、app-serverの生stderrは読み捨てる実装です。

### 6.3 商品ごとの生成・保存ログ（L05）

出力実装：[copy_service.py `_trace_copy_event`](../../automation/inago/copy_service.py)。

一商品について、`schema_version="1"`、`at`（JST）、`event`、`run_id`、`offer_key`、`draft_version`、`settings_version` を保存します。必要な場合に `attempt_no`、`status`、`error_code`、`cause_code`、`artifact_ref`、`ai_run_invoked` を追加します。

eventは `generation_requested`、`generation_attempt_reserved`、`ai_result_received`、`ai_runner_failed`、`ai_contract_rejected`、`response_checkpoint_saved`、`saved_response_resume`、`draft_commit_started`、`draft_commit_failed`、`draft_commit_rejected`、`draft_committed`。新たにAIを呼んだか、保存済み応答を再利用したか、DBへの下書き確定まで進んだかを追えます。本文自体は入れません。

### 6.4 生応答と専門応答（A02、A03）

[artifact_io.py](../../automation/inago/artifact_io.py) が、一時ファイルから最終ファイルを公開する方法で保存します。

- A02：AI最終応答を解析・検証する前に生バイトで保存します。契約拒否された応答も証拠として残る場合があります。原本を取れなければ作られません。job本文の `payload`、専門子の結果、入力参照などを含むため、L03とは公開範囲が異なります。
- A03：紹介文の専門応答JSONです。成功した下書きの生成根拠や、中断後に同じ応答で保存を再開するために使います。本文・商品情報を含み得ます。`generation_attempt`、`ai_job`、`draft`、`artifact`の参照で結びます。
- 保存後にDB登録で失敗した場合、ファイルだけが先に残ることがあります。ファイルの存在だけでは採用・下書き確定の証拠になりません。

### 6.5 作業ファイルとCodex自身の記録（W01、X02）

`D\jobs`には `job-input.json`、`ai-job.schema.json`、`final.response`、許可された `.agents\skills`・`.codex\agents` を一時配置します。通常の日次はroot終了まで必要なディレクトリを保持し、終了時に削除します。異常終了や削除失敗で残存する可能性があり、恒久ログとしては使いません。

Codex自身が管理するrolloutは `C\sessions\YYYY\MM\DD\rollout-*-<thread_id>.jsonl` です。runnerはroot threadと専門子の親子関係、モデル、reasoning、ネイティブ委譲の確認に読みます。日付ディレクトリはrunnerが実行時刻の前後日も探索するため、JST対象日だけと一致するとは限りません。プロンプト・応答・tool情報を含み得る生の実行記録であり、独自allowlistで作るL03/L04と同じ安全な内容ではありません。作成・形式・保持はCodex側の管理で、本リポジトリの90日削除処理は適用されません。

## 7. 検索画面の観測と失敗証拠（O01～O03、A01）

出力実装：[public_sources.mjs](../../automation/inago/adapters/public_sources.mjs)、[live_sources.py](../../automation/inago/live_sources.py)。

### 7.1 取得一回分の観測JSON

O01/O02は、Pythonがworkerを回収して結果を検証した後に新規保存します。共通の外枠は次のとおりです。

起動前の取消や早期return、観測の保存処理自体の例外では、O01/O02が作られない場合があります。「失敗した取得には必ず観測ファイルが一つある」とは扱いません。

| 項目 | 内容 |
| --- | --- |
| `kind`、`request`、`environment` | `trends/room`、run・request/attempt・query・個別期限などの取得条件、本番は `public_ui` |
| `recorded_at`、`retention_expires_at` | 保存時刻とrawの90日期限。`recorded_at`はUTCのoffset付きISO 8601 |
| 成功結果 | `response`、`product_facts`、`diagnostics` |
| 失敗結果 | `error_code`、必要な場合 `diagnostics`・`retry_after_seconds` |
| `node_events` | Nodeのstderrから許可項目だけを採ったstage・ブラウザー診断・失敗event |
| `process_returncode`、`trace_state`、`trace_ref` | workerの終了値、共通traceの状態、その参照パス |

成功したROOM観測には商品URL、商品キー、商品情報などを含み、Trendsには検索条件と取得語を含みます。認証値・アカウント・ブラウザープロファイル・他者投稿本文を通常診断へ出さない設計でも、**観測JSONそのものが匿名の共通ログという意味ではありません**。

Nodeは `public_source_stage`、`public_source_failure`、`public_source_diagnostic`、`public_source_trace_suppressed` をstderrへJSON行で返します。Pythonは先頭5,000行までを解析し、許可されたevent/項目だけを `node_events` と共通traceへ移します。stderr原文を丸ごと保存するファイルはありません。診断はconsole/page error、通信失敗、navigation/popupなどの分類と件数を残し、エラーメッセージやURLの原文は残しません。

Nodeのstage出力は2,047件で抑止markerを出します。Python側のallowlistと共通traceの上限も別にあるため、観測されたすべてのブラウザーイベントが共通JSONLに無制限で入るわけではありません。通常日次でスクリーンショット、動画、HAR、Playwrightの `trace.zip` を自動保存する処理はありません。

### 7.2 アクセス停止ファイル

O03は `run_id`、`kind`、`error_code`、`recorded_at` のJSONです。停止判定を先に永続化してから詳細観測を保存します。このため、後続の観測保存が失敗しても停止ファイルだけ残る場合があります。通常の有限retryへ戻すTrendsの429と、runを止めるアクセス制限は同一扱いではなく、実装の停止条件によって作られます。

O03はraw観測ファイルの90日回収globには含まれません。過去runの停止理由を読まずにファイルだけ削除して再開する用途には使いません。

### 7.3 Trendsの失敗参照ファイル

A01は `schema_version`、`kind=trends_failure_observation`、`artifact_ref`、`request_id`、`attempt_no`、`run_id`、`settings_version`、`failure_error_code`、`source_status`、`source_observation_state`、保存・期限時刻、`trace_ref`、`trace_state`、安全な `node_events`、`process_returncode` を持つJSONです。

元観測が見つからない場合は `source_observation_state=missing` を残す経路もあります。`trends_acquisition_attempt.evidence_ref`から `artifact.artifact_ref`を引き、`artifact.path`で開きます。これは検索で取得した関連語一覧そのものではなく、失敗位置・証拠の取得可否を保存するファイルです。

出力実装：[metrics_live.mjs](../../automation/inago/adapters/metrics_live.mjs)、[metrics_live_port.py](../../automation/inago/metrics_live_port.py)、[metrics.py](../../automation/inago/metrics.py)。

### 8.1 一回の外部収集ディレクトリ

`metrics-<UTC日時>`を新規作成し、その中に次の4ファイルを保存します。

| ファイル | 内容・形式 |
| --- | --- |
| `events.jsonl` | `at`（UTC ISO 8601）、`source=affiliate/room`、`event`、安全な件数や分類値。ソース開始・完了・失敗、月別の取得、ROOM公開ページ観測などを逐次追記 |

## 10. 実行中の監視・所有者ファイル（S02、S03）

出力実装：[operations.py](../../automation/inago/operations.py)、[run_lock.py](../../automation/inago/run_lock.py)。

`daily-operations.json`は時系列の追記ログではなく、**最後に読めた状態一件**です。観測内容は `schema_version`、`run_id`、`target_date`、`run_status`、`phase`、`process_pid`、`checkpoint_digest`、`heartbeat_at`、`progress_at`、`monitor_updated_at`、条件付きの `failure_kind`。productionではJSTの時計を渡します。

最初の観測、通常30秒ごと、監視停止時に更新を試みます。所有プロセスとSQLite状態を確認できた場合にだけ保存するため、30秒ごとに必ず更新できるという保証ではありません。更新失敗時は前のファイルが残り得ます。`heartbeat_at`の新しさと、checkpointが最後に変わった `progress_at` を区別します。

`.daily-run-owner.json`は `pid`、`process_start_time`、`run_id` の所有者情報です。`.daily-run.lock`は排他用のbyte lockです。正常な解放では所有者ファイルを除去する経路があり、異常終了では残存し得ます。存在だけで「現在実行中」「正常終了」とは判断せず、process開始時刻やOSの実プロセスとも照合します。

## 11. 本人報告・履歴画面から出る記録（V01、H01、H02）

出力実装：[dashboard_history.py](../../automation/inago/dashboard_history.py)、[history.js](../../rakuten-room-inago/dashboard-assets/history.js)、[human_api.py](../../automation/inago/human_api.py)、[report_import.py](../../automation/inago/report_import.py)、[report_apply.py](../../automation/inago/report_apply.py)。

- `posting-history.html`はDBの全日次履歴を表示する最新snapshotです。下書き本文・URL・報告状態等を持ち、更新前のHTMLを日々別ファイルとして残す出力ではありません。画面にある表示状態だけで投稿・報告受付済みとは判断しません。
- APIへの報告がまだ受付されていない場合は、使用ブラウザーのorigin/profileに属するIndexedDBの `browser-outbox`へ `action_id`をキーに保存します。リポジトリ内の固定JSONLファイルではありません。受付のACKを確認してからoutboxから削除します。
- 本人が書き出すJSONは `human-reports-<UTC ISO日時のコロン/小数点をハイフンにした値>.json`。出力先はブラウザーのダウンロード先または保存操作で指定した場所で、日次が自動的にinboxへ置くものではありません。
- `D\incoming-human-reports`へ置いた `human-reports-*.json`を日次が検証・batch受付します。commitした後、`processed-human-reports`へ元名で移動し、同名があれば末尾に連番を付けます。これらは本人報告payloadを含む業務ファイルです。
- API受付traceは元の下書きのrunに、JSON取込・翌日反映traceは実行中の日次runに結び付きます。同じ `action_id`を使って日付をまたいで検索します。
- Human APIはHTTPの標準 `log_message` を無効にしています。すべてのGET、health確認、認証失敗、400/409応答を記録する `access.log` はありません。receiptのbeginがあってendがない場合も、traceだけではHTTP結果やDB状態を確定できません。SQLiteの受付と反映statusを確認します。

## 12. バックアップ・隔離復元確認（B01、B02）

出力実装：[backup.py](../../automation/inago/backup.py)、[restore_check.py](../../automation/inago/restore_check.py)、[production_runtime.py](../../automation/inago/production_runtime.py)。

開始世代 `daily-YYYYMMDD`と終了世代 `daily-final-YYYYMMDD-<UUID>`を別に管理します。各bundleは次の構成です。

```text
<backup-generation>/
  state.sqlite
  manifest.json
  artifacts/<artifact_ref>/<元のファイル名>
```

`manifest.json`には `manifest_version`、`backup_type`、`generation_stage`、`created_at`、schema版、各テーブル件数、設定版一覧、投稿/予約/pending等の件数、含めたartifactの参照・パス・期限、検証結果、snapshot方式を保存します。DBはSQLite backup APIによる整合したsnapshotです。

バックアップはruntime全体の丸ごとコピーではありません。登録済みの対象artifactをbundleへ含めますが、独立した `logs`ツリー、`observations`、metrics収集ディレクトリ、Codex rolloutのすべてをそのまま複製する処理ではありません。ログの保全先としてバックアップだけを前提にしないでください。

月次の復元確認は `B\restore-check\YYYY-MM`に `restored-data\state.sqlite`と対象artifactを復元し、`report.json`を保存します。reportは対象backup、確認時刻、integrity/FK、schema/件数、期限適用、投稿・予約・pending等、補足確認が必要な状態を持ちます。`selection_allowed=false`、`requires_supplementation=true`を含み、本番DBを試験復元したことにはしません。同月の確認を再利用した場合は新規reportが作られないことがあります。

## 15. 一つの失敗を追う順序

1. **起動と完了通知を確認する。** U08のMN01 `daily_launch`を`source_launch_id`・対象日・開始時刻で照合します。`running`は完了通知未保存であり成功を意味しません。最終通知がない場合はS02、run、Scheduler状態も確認します。`source_run_id=null`ならrun未生成の事実を保ち、存在しないrunを探したり補ったりしません。次にL01の最終結果を照合し、L01にはrun IDの固定欄がないためS01のrun、MN01の起動行、Scheduler結果を合わせます。
2. **どの工程で止まったかを知る。** 同じrun IDのL02を日付フォルダー全体から探し、`at`、component、operation、phase、`active_stage`／`last_completed_stage`、primary/cause/cleanupを確認します。追記順だけを発生順としません。
3. **検索の試行を開く。** Trendsは `request_id → trends_acquisition_attempt → evidence_ref → artifact.path`。ROOMは `attempt_id → search_attempt`、O02の同じID。観測JSONの `trace_ref`も照合します。再試行は `retry_of`でたどります。
4. **AI生成を追う。** 商品のL05から生成試行とartifactを見つけ、`ai_job`とL03を確認します。root thread/turnの起動・取消に問題があればL04、必要な範囲でX02へ進みます。応答が存在することと、DBに採用されたことを区別します。
5. **本人報告・成果・保全を追う。** 本人報告は日付をまたいでも `action_id`、成果はM01/M02/M03と `source_ref`、保全はmanifest/reportとDBの検証結果を照合します。
6. **記録の可用性を確認する。** `trace_state=degraded/unavailable`、抑止marker、artifactの `expired/missing`、欠落したmanifestや終了eventを確認します。記録がないことを「失敗がなかった」とは解釈しません。

たとえば、Google Trendsで検索語を入力し、期間を「過去3か月」にした後に関連ワード欄が出なかった場合、L02の最後の完了操作と現在の待機操作、O01/A01の `node_events`、DBの該当 `request_id`を合わせると、期間変更後の表示待ちで時間切れになったのか、対象欄を一つに決められなかったのかを調べられます。公開サイトがそうなった根本原因は、保存された証拠の範囲で判断します。

## FC03 operation log runtime behavior

- MN04 maintenance JSONLはstage記録の主sinkでbest-effort。書込失敗でも本処理・次stageを止めない。
- `D/maintenance/failure-journal/events.jsonl`は通常logger/SQLiteと独立する安全化JSONL fallback。primary path解決または書込が失敗した時は`D/maintenance/failure-journal-secondary/events.jsonl`へ保存する。復帰時は両方からDB eventを冪等照合し、begin-only操作に中断観測を追記する。
- FC03当時のschema14 sourceを経て、現行schema16 sourceのoperation tableはappend-only。FC09適用前のruntime DBはschema13であり、正式適用後のread-backをFC09実行記録に残す。
- eventは相関ID、operation、親operation、対象identity、phase、実行版、例外型連鎖、利用可能な数値errno、file/line/function、参照を結ぶ。DB再照合失敗も元correlation IDのfallback eventへ記録する。DB latest順はtimestampとSQLite rowidで安定化する。例外本文、SQL、商品/投稿、secret/PIIは含めない。
- failure journalの入力/成果物参照はIDとpathを区別する。pathはprivate root相対の安全なPOSIX参照だけを表示用に保存し、絶対path、`\`、`.`/`..`要素、制御/記号文字、secret/password/credential/cookie/token/private key/環境fileを示す値は除外する。path値をjob等のidentity IDとして扱わず、危険な値はnull要素にせず省く。
- invocation開始時にmaintenance Python/SQL、maintenance schema、worker、workflow、daily境界sourceのhashとworker除外日/schema版・workflow stage順を含むaggregate fingerprintを一度作る。開始後のfailure eventとhandoffは同じ値を使う。取得失敗は`code_revision=unknown`と具体的capture reasonをfallbackへ記録し、次stageは続ける。補助logger fileだけのhashは実行版として使わない。


### FC04 調査・計画の引継ぎ記録

各調査・計画stageは、読み込んだ入力参照、内容の由来（担当AIまたはcontroller fallback）、確認事項、未知と理由、次の担当・操作、成果参照をhandoffへ記録する。確認事実がない調査fallbackは、原因を推測せず「確認できた事実なし」というunknown factを利用可能な参照・次の確認と共に保存し、計画担当へ渡す。担当AIが例外・空応答・不正応答を返した場合もfallbackの作成操作と失敗原因を紐付け、後続stageを実起動する。
