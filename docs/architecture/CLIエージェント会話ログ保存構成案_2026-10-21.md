# CLIエージェント会話ログの保存構成案

作成日：2026-10-21（JST）
状態：構成案。会話収集機能・設定・保持処理は未実装。今回の成果は本書であり、日次・保守フローの動作は変更しない。

## 1. 結論

**保存は可能。CLIを起動するPython側で、メインエージェントと、その配下で動くサブエージェントの会話を収集し、プロジェクト内へ保存する構成を推奨する。**

保存形式は、機械処理・再開に使う **JSONL** と、人が読む **Markdown** の組合せとする。会話はthread単位に分け、親子関係を台帳で結ぶ。サブエージェントがさらに呼んだ子も同じ方法で追跡する。

**本人の指定により、要約ではなく会話全体を保存する。文字数・件数での切り捨て、古い会話の自動削除は標準では行わない。** 大きくなった場合はファイル分割で対応し、全文を再構築できる状態を保つ。

ただし、保存できるのはCodexが外部へ提供・永続化した情報である。内部思考の完全記録、取得できないシステム指示、失われた過去の会話まで復元できるとは扱わない。親の最終回答に子の結果が含まれるだけでは、子の会話を保存できたとは判定しない。

## 2. 現行実装で確認できたこと

確認対象は作成時点の作業ツリーと、ローカルCLI `codex-cli 0.162.0-alpha.17.2`。実フローを起動した検証ではなく、コード・公式資料・CLI生成schemaの静的確認である。

| 対象 | 現行の動作 | 今回の構成案との差 |
| --- | --- | --- |
| 日次の起動 | `daily_ai.py` が `AppServerSession` を使い、一つのroot threadを複数job/turnで利用する | jobごとに会話全履歴を複製せず、run内でthreadの会話とjob/turn対応を保存する |
| 通信ログ | `app_server.py` の `_log` は識別子・状態などの許可項目を保存する | 会話本文用の別writerが必要 |
| 日次の子の確認 | `ai_runner.py` がCodexのrolloutを読み、rootと直接の子のID、役割、委譲を確認する | プロジェクト内への会話保存と、孫以降の再帰収集は追加が必要 |
| 保守の現行入口 | `production_workflow.py` → `skill_chain.py` → `skill_chain_runtime.py` | 各CLI起動役割に共通の収集器を接続する |
| 保守の既存ログ | `runtime/maintenance-flow/<job_id>/calls.jsonl` と `app-server/<role>.jsonl` を保存する | 役割・再起動・threadごとに会話を探せる台帳を追加する |
| 保守の本文記録 | 最終応答は最大20,000文字、イベント要約は最大200件、各出力は最大4,000文字。stderrも伏字・上限付き | 既存の要約を会話全文として転用しない |
| 通知の受信 | `run_turn` は対象rootのthread/turnに合う通知だけを結果へ保持する | rootの結果だけを保存しても子の会話全体は揃わない |
| 運用データ | `rakuten-room-inago/runtime/` は既にGit管理対象外 | 新しい会話ログもこの配下へ置く |

既存のL03/L04や保守traceは状態・障害診断の記録として維持する。本文を含む新しい会話ログは、それらのallowlistへ混在させない。運用一覧の一部には以前のstderrの説明が残るが、現行コードは伏字付きの限定的なstderrを保持しているため、本書ではコードの動作を区別した。

## 3. 保存する情報

| 情報 | 保存方針 |
| --- | --- |
| Pythonから渡した依頼文・追加依頼 | 送信前に記録。送信成功・失敗は別イベントにする |
| エージェントの進捗発言・最終回答 | 利用可能な本文を記録。最終回答だけに限定しない |
| 親から子への依頼、子から親への応答 | 送信元・宛先thread、call IDと結ぶ |
| ツール呼出し・結果 | 公開される引数・結果を対象とし、秘密情報の除去と長文分割を行う |
| 起動・終了・取消・失敗 | 元の会話に対応する状態として記録する |
| model・effort・CLI版 | 要求値と観測値を分け、未観測はnullと理由を記録する |
| skill・role指示 | 自プロジェクトから実際に渡した指示本文を専用種別で保存し、参照元のpathとSHA-256も記録する |
| 画像・添付ファイル | 本文へbase64を埋め込まず、既存artifactへの安全な相対参照とhashを保存。参照先の保持期限も明示する |
| 内部思考・非公開指示 | 完全取得を要件に含めない。利用可能な要約があっても会話本文と区別する |

認証用の秘密情報を除き、会話本文・ツール引数・ツール結果を既存要約の文字数や件数で切り捨てない。構造化された内容も一部fieldだけの要約に置換せず、会話に属する内容を保持する。取得不能やディスク書込失敗が起きた場合は欠落として対象・理由・取得済み範囲を残し、意図した省略として扱わない。「取得可能な会話の全文保存」と「認証通信などを含む無加工の全通信保存」は区別する。

## 4. 推奨ディレクトリ構成

保存rootを次に固定する。

```text
C:/project/rakuten-room-inago/rakuten-room-inago/runtime/conversation-logs/
```

日次フロー用・保守フロー用を最初に分け、その直下へ「起動日＋実行識別子」を置く。以下のIDは説明用の仮値である。

│     ├─ collection.jsonl                      # 取得・欠落・再収集の履歴
│     ├─ README.md                             # 各会話への索引・取得状態
│     └─ 01-ai-o/                              # CLI起動担当：AI-O
│        ├─ inv-i01__main__thr-root__part-0001.jsonl
│        ├─ inv-i01__main__thr-root.md
│        ├─ inv-i01__sub-ag-obs__thr-obs__part-0001.jsonl
│        ├─ inv-i01__sub-ag-obs__thr-obs.md

      ├─ run.json
      ├─ agents.json
      ├─ collection.jsonl
      ├─ README.md
      ├─ 01-investigator/

| `03-tester` | `common-tester` |
| `04-product-reviewer` | `common-reviewer` |

## 5. 起動日・実行ID・再開の規則

| 項目 | 規則 |
| --- | --- |
| 起動日 | 初回フロー起動時の `Asia/Tokyo` の暦日。深夜をまたいでも移動しない |
| 対象日 | `target_date` として別記録。過去日を扱う保守でもディレクトリは実際の起動日で決める |
| 日次実行識別子 | 通常は既存 `run_id`。発行前に失敗した起動は `launch-<source_launch_id>` を使用する |
| 保守実行識別子 | 既存 `job_id`。元の日次 `source_run_id` がnullでも作成できる |
| ID発行前 | 利用可能なlaunch IDもなければhostが `capture-<UUID>` を発行。後からrun/jobへ結び、元IDを捏造しない |
| 発行後の扱い | 保存パスは初回確定後に変えず、`run.json` に後発IDを追記する。照会はID対応表で行う |
| 再開 | 同じrun/jobは元のフォルダーを使う。再開日の別runへ会話を重複保存しない |
| 別の起動試行 | host発行の `invocation_id` を更新。同一roleの再実行・HTML修正往復も別ファイルとして残す |
| 同一プロセス内の再試行 | `attempt` とturn IDで区別。threadを作り直した場合は新thread用ファイルを作る |
| 同じthreadの再接続 | ファイルはinvocationごとに分ける。台帳で同一threadと既存取得範囲を共有し、過去履歴を再複製しない |
| Windowsの名前制限 | IDをそのままpathへ連結しない。禁止文字・予約名・長さを検査し、必要ならSHA-256由来の短い一意キーへ変換。元IDとの対応を台帳へ残す |

プロセスIDや時刻の近さだけでrun・親子を決めない。複数フローが同時に動いても混在しないよう、収集器へhostがrun/job/invocation情報を明示して渡す。

## 6. ファイルの役割と最低限の項目

| ファイル | 内容 |
| --- | --- |
| `run.json` | schema版、flow種別、保存キー、初回起動日時、timezone、target_date、run/job/source_launch/source_run、コード版、CLI版、設定hash、invocation履歴、保持設定、総byte数 |
| `agents.json` | thread ID、parent/root thread ID、CLI起動担当、実際のrole/skill、深さ、invocation、開始・終了観測、要求/観測model、ファイル参照、取得範囲・状態 |
| 会話 `*.jsonl` | 1行1イベント。正規化・秘密除去後の保存正本。追記し、閉じたpartのSHA-256を台帳へ登録 |
| 会話 `*.md` | JSONLから再生成する閲覧用。依頼、進捗、ツール、子への委譲、回答、失敗を順番に表示 |
| `collection.jsonl` | 収集開始・再取得・未対応形式・欠落区間・保存失敗・復旧・容量計測の記録。会話本文は入れない |
| `README.md` | run概要、役割と親子ツリー、会話リンク、取得できた範囲、取得できなかった理由 |

会話イベントの例（この構成案独自のschemaであり、Codexの生イベント形式ではない）：

```json
{"schema_version":1,"event_id":"evt-001","observed_at":"2026-10-21T09:00:01+09:00","source_at":null,"flow":"daily","run_id":"run-d01","job_id":null,"invocation_id":"i01","thread_id":"thr-obs","parent_thread_id":"thr-root","turn_id":"turn-01","item_id":"item-01","seq":1,"kind":"assistant_message","source":"app_server","content":"確認できた観測値を返します。","redacted":false}
```

追加で `call_id`、送受信先thread、job/task/attempt、itemの完了状態、内容分割の番号、元データの種別・schema識別、省略理由を持たせる。元の発生時刻がなければ `source_at=null` とし、収集時刻を発生時刻に置き換えない。

`seq` はthread内の記録順であり、別thread間の厳密な実行順を保証しない。ライブ通知のdeltaと最終itemは、thread/turn/item IDとイベント種別・分割位置で照合する。最終itemの本文とdeltaを単純連結して二重表示しない。IDがなく安全に重複判定できない記録は、その不確実性を表示する。

## 7. 会話の取得方法

### 7.1 基本方針

エージェント自身に会話を書き写させず、**CLIを制御するhost側の共通収集器**で保存する。自己申告に依存せず、例外・空応答・途中停止も記録対象にできる。

公式資料では、app-serverのthreadメタデータ取得と、turn/item履歴のページ取得が提供される。また `codex exec --json` は実行イベントをJSONLで出力する。このプロジェクトは既存のapp-server方式を使い、exec方式の追加時だけ別アダプターで対応する。[Codex App Server](https://learn.chatgpt.com/docs/app-server)、[Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)

### 7.2 収集順序

1. hostがフローの保存先・invocationを確定し、実際に送る依頼と指示参照を記録する。
2. root thread IDの発行直後に台帳へ登録する。送信イベント・進捗・回答・ツール結果を受信時に順次保存する。
3. 委譲イベントで子thread IDを取得し、子のメタデータと親IDを照合する。取得した子にも同じ処理を再帰適用する。
4. turn終了時と終了前に、保存履歴をページ単位で読み戻す。対応版では `thread/read` でメタデータ、`thread/turns/list` の `itemsView=full` または `thread/items/list` で本文を取得し、cursorが尽きるまで確認する。
5. ライブ取得と履歴をIDで照合し、欠落を補う。既知の子だけでなく、親IDにより関連を証明できる子がないか終端で再確認する。
6. JSONLを確定し、Markdownとrun索引を生成する。子がまだ動作中なら、収集完了にはせず取得可能な部分を先に残す。

root threadで子の起動を観測したことと、子の依頼・途中処理・回答を回収できたことは別に判定する。親子台帳はイベントの子IDと `parentThreadId` 等のメタデータを使い、役割名や同じcwdだけの一致では採用しない。

### 7.3 CLI版の互換性とrolloutの補助利用

作成時点のCLIからschemaを生成し、上記3つの履歴取得method、およびthreadの `parentThreadId`・`agentRole` が定義されることを確認した。**schemaの存在は、この環境の実threadで全文を取得できた証明ではない。** itemページ取得の対応や子の履歴へのアクセスは、実装時の隔離試験で確認する。

古い版は `thread/read` の `includeTurns=true` を互換経路として検討する。現在の公式資料ではページ方式が推奨されるため、応答schema・サイズ・取得範囲を検査し、未対応を成功と扱わない。既存セッションを変えてしまう `thread/resume` を履歴閲覧の代わりには使わない。

API経由で不足する場合に限り、既存 `ai_runner.py` の仕組みを参考に、`CODEX_HOME/sessions/.../rollout-*.jsonl` を補助入力として読む。対象は既知のrootと親子関係を確認した子孫に限る。形式は内部実装へ依存するため、CLI版ごとのアダプターで解析し、不明形式は `unsupported_format` とする。日付だけで同日の無関係な会話をコピーしない。

元のrolloutを移動・変更せず、プロジェクト側へ必要な会話を正規化して保存する。グローバルの `CODEX_HOME` は変更しない。プロジェクト内ログを再開元にする機能は今回の提案範囲に含めず、再開は既存Codexの履歴とthread IDを使う。

## 8. 再開・異常終了・保存失敗

会話の取得状態は、業務フローや試験の成功と分けて記録する。

| `capture_status` | 意味 |
| --- | --- |
| `collecting` | 取得中。子を含む終端照合は未完了 |
| `complete` | 既知の全対象threadの、当該runに属する外部取得可能な範囲を照合済み。内部思考の完全性を示さない |
| `partial` | 一部取得。子の本文欠落、未対応item、切捨て、保存失敗などの具体的理由がある |
| `unavailable` | 対象は分かるが会話本文を取得できない |

起動しなかったroleは台帳に `execution_status=not_started` と理由を残し、空ファイルを成功記録にしない。秘密除去した箇所は `redacted` と件数・分類を表示し、意図した除去と取得失敗による欠落を区別する。

保存はJSONLを逐次追記し、turn境界などでflush/fsyncする。台帳・Markdownは一時ファイルから置換し、並行writerは単一のhost writerへ集約する。突然停止して最終行が未完なら、既存ファイルを退避保持し、新partと修復記録を作る。古い行を黙って消さない。

再開時は未完invocation、最後に取得済みのturn/item/cursor、未回収の子を照合する。同じthreadを再取得しても同一itemを重複登録しない。compactionやforkで過去文脈が再登場した場合も、継承履歴とそのrunで新しく発生した会話を区別する。時間範囲だけで再開前後を切り分けない。

ログ保存が失敗しても、日次・保守全体や独立した後続工程を止めない。既存の安全な診断系へ本文を含まない失敗分類・相関IDを渡す。別sinkも失われた区間は復旧時にunknownとして残す。回収を優先して既存の取消・終了期限を延ばしたり、子の異常終了を成功に変えたりしない。

## 9. 非公開管理・保持方針

会話には商品情報、作業中のコード、ファイル内容が含まれるため、既存runtimeと同じ非公開運用データとして扱う。`.gitignore` は既存のruntime指定で覆われる。文書だけをGit管理し、会話本文はコミット・push・HTML公開・共有報告への自動転記をしない。

保存前に認証header、cookie、API key、token、秘密鍵など、認証に使う秘密値を伏字にする。構造化された秘密fieldと既知の秘密値を対象とし、正規表現だけで検出を保証しない。通常の会話・商品情報・コード・ツール結果は全文保存し、ログの非公開管理で扱う。認証情報が一部にあることを理由に、メッセージ全体を要約・破棄しない。伏字箇所は明示し、生の認証通信を保存する機能は設けない。

保持期間は**期限なし・自動削除なしを標準**とする。`retention_days=null` として既存のL02やMN04の90日削除処理へ接続しない。将来の削除・期限設定は本人の依頼に基づく別変更とする。今回提案する全文保存で、古い会話が知らないうちに消える構成にはしない。

JSONLは16 MiBを目安にpartを分割する案とし、長い単一itemも内容chunkと連番で分けて切捨てを避ける。16 MiBは保持上限ではない。Markdownも全文を出力し、必要に応じてpartを分けて索引で結ぶ。容量不足時は取得失敗をpartialとして記録し、古い会話を黙って削除しない。バックアップする場合も非公開データとして扱う。

テキスト中心であれば全文保存を前提にできる。実容量は会話数とツール出力に依存するため、run/thread別のbyte数、item数、日別合計を記録する。計画上の例として、日次・保守が各1回/日、各フローのJSONLとMarkdownの合計が5 MiBなら30日で約300 MiB、365日で約3.6 GiBとなる。これは仮定による目安であり、現行ログの実測値ではない。まず全文を残して計測し、量が増えた場合の圧縮も内容を失わない方式で検討する。

すべての出力パスで固定root内への包含、Windowsのreparse point、path部品の妥当性を検査する。Markdownの本文は引用・コードブロックとして表示し、会話中のHTML・リンク・命令を実行する仕組みは設けない。

## 10. 実装する場合の変更箇所

| 対象 | 追加する責務 |
| --- | --- |
| 新設候補 `automation/inago/conversation_log.py` | 保存キー、schema、JSONL writer、親子台帳、伏字、分割、再開照合、Markdown出力 |
| `app_server.py` | 依頼送信と通知の収集callback。root以外の観測も収集器へ渡す。本文取得の失敗を既存業務結果へ混ぜない |
| `daily_ai.py` | 日次run・launch・invocationとroot threadを収集器へ結び、root終了前の回収を呼ぶ |
| `ai_runner.py` | 既存job/task/attempt対応を渡し、必要な場合だけrolloutから補助回収する |
| `maintenance/skill_chain_runtime.py` | 7役の起動と再実行へ同じ収集器を接続し、job・元日次run・invocationを渡す |
| 設定・容量管理 | 新規ログ専用の有効設定、期限なしの保持、part分割、保存byte数の計測を追加 |
| 運用資料 | 既存ログ一覧へ会話ログの保存先・取得状態・非公開範囲を追記 |

まず共通収集器と隔離fixtureで全文保存仕様を固め、日次root・保守各役へ接続する。次に子孫回収と再開照合を確認し、最後に容量計測と期限なしの保持設定を確認する。既存ログの移動・本番DB migration・スケジューラー再登録はこの構成案だけでは行わない。

## 11. 実装時の受入確認

| ケース | 確認する結果 |
| --- | --- |
| 日次root＋OBS/KEY/COPY | 依頼・進捗・回答が各threadへ分かれ、親子が一致する |
| 保守7役＋独立レビューの子 | 起動担当の配下へ保存され、別役へ混ざらない |
| 子が孫を呼ぶ／複数同役の子 | 再帰取得でき、thread IDで個別に追跡できる |
| 同一rootで複数job | turnとjobが対応し、既存履歴を重複保存しない |
| 同じjobの再開・HTML修正往復 | 元の起動日フォルダーを使い、invocationを分けて上書きを防ぐ |
| 日跨ぎ・対象日と起動日が異なる保守 | JST初回起動日と対象日を取り違えない |
| run ID未発行／source_run_id=null | launch/capture/job IDで保存でき、nullを捏造しない |
| 途中停止・不完全JSONL・子の遅延 | 既存データを保持し、partialと欠落区間を表示する |
| 履歴の複数ページ・未対応API・rollout形式変更 | 全cursorを読み、取得不能を成功としない |
| 20,000文字超の本文・200件超のitem | 既存要約の上限を流用せず、part/chunkから再構築できる |
| 並行run・別チャットのrollout | 親子とrunの明示照合で混在を防ぐ |
| token入りtool結果・危険なpath・保存不可 | 秘密を残さず、理由を記録し、独立した後続工程は続く |
| 期限なし・容量計測・Git除外 | 90日経過後も自動削除されず、byte数が一致し、本文がGit対象外である |

本書作成ではこれらの動作試験は未実施。実装時は隔離した入力・出力で試験し、失敗nodeを先に直してから、計画した回帰試験を一度実施する。実CLIでの子履歴取得は、その時点の版・取得範囲を記録して別途確認する。
