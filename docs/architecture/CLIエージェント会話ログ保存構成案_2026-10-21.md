# CLIエージェント会話ログの保存構成案（最小版）

更新日：2026-10-21（JST）
状態：構成案。保存機能は未実装。

## 1. 方針

**Codexが保存した会話JSONLを、プロジェクト内へコピーする。メイン・子・孫の会話を全文保存し、要約・文字数や件数による切り捨て・自動削除は行わない。**

保存形式はJSONLだけとする。専用DB、会話台帳、Markdown変換、容量集計、圧縮、ファイル分割は作らない。ログを閲覧する際は、そのままテキストエディターで開く。

## 2. ディレクトリ構成

保存先は既にGit管理対象外の、次の場所とする。IDは説明用の仮値。

```text
C:/project/rakuten-room-inago/rakuten-room-inago/runtime/conversation-logs/
├─ daily/                              # 日次フロー
│  └─ 2026-10-21__run-d01/              # 初回起動日（JST）＋run ID
│     └─ ai-o/                         # CLIから起動する役割
│        ├─ main__<thread-id>.jsonl
│        ├─ sub__<thread-id>.jsonl      # 子・孫はthreadごとに1ファイル
│        └─ status.txt
└─ maintenance/                        # 保守フロー
   └─ 2026-10-21__job-m01/              # 初回起動日（JST）＋job ID
      ├─ investigator/
      │  ├─ main__<thread-id>.jsonl
      │  ├─ sub__<thread-id>.jsonl
      │  └─ status.txt
      ├─ implementer/
      ├─ tester/
      ├─ product-reviewer/
      ├─ delivery/
      ├─ reporter/
      └─ html-reviewer/
```

役割フォルダーはCLIから直接起動する担当単位とし、その配下の子・孫も同じフォルダーへ置く。起動しなかった役割のフォルダーは作らない。

## 3. 保存方法

1. Pythonの起動処理が、フロー種別・初回起動日・run/job ID・役割・メインthread IDを保存処理へ渡す。
2. Codexの `CODEX_HOME/sessions/` から、そのメインthreadの会話JSONL（rollout）を探す。既存 `ai_runner.py` の探索処理を共通化して使う。
3. 原本に記録された親thread IDをたどり、対象メインの子・孫を再帰的に探す。同じ日にある無関係な会話は対象にしない。
4. 各turn終了時とCLI終了処理時に、見つかった原本を一時ファイルへ全文コピーしてから保存先へ置き換える。元のCodexファイルは変更しない。
5. `status.txt` に更新日時、役割名、各threadの親ID、コピー成功／失敗と理由を記録する。会話本文はここへ重複保存しない。

同じthreadの再保存は同じファイルの更新とするため、追記の重複排除処理は不要。別threadで再試行した場合は、thread IDが異なる別ファイルを残す。同じrun/jobの再開は初回のフォルダーを使い、日付をまたいでも保存場所を変えない。

run ID発行前は既存launch IDを使用し、launch IDもない場合だけ保存用UUIDを使う。後からrun IDが発行されてもフォルダー名は変えず、対応するIDを `status.txt` に追記する。Windowsで使えないID文字は安全なファイル名へ変換し、元IDも同ファイルに残す。

## 4. 保存範囲と失敗時の扱い

保存するのは、**Codexの原本に記録された依頼文、途中発言、ツール呼出し・結果、最終回答の全体**。メインの最終回答だけで子の会話を代用しない。原本が持つ親子情報や実行情報もそのまま残す。

原本に存在しない情報や非公開の内部思考は取得できない。履歴の未作成、未対応の原本形式、途中停止、コピー失敗などは `status.txt` へ対象と理由を残し、全文保存済みと扱わない。プロセスの強制終了では最後のコピー以降が未保存になり得るため、次回の同run/job再開時に原本が残っていれば再コピーする。保存中に原本が更新された場合は、そのコピーを未確定として次の保存機会に更新する。

保存失敗で日次・保守の後続工程は止めない。`status.txt` 自体を書けない場合は、既存の診断ログへ保存先と失敗理由だけを記録する。出力パスは固定root内に限定する。

会話ログは非公開のローカルデータとして保存し、Gitへのコミット・push・報告HTMLへの自動公開は行わない。保持期限・サイズ上限・自動削除処理は設けない。

## 5. 実装範囲と確認

追加するのは**共通のコピー処理1つと、日次・保守の呼出し箇所**。既存の状態ログ、DB、skillの役割構成は変更しない。app-serverの履歴API取得や独自の会話schemaは、最小版には追加しない。

実装時は、①メイン・子・孫の全文一致、②別runとの分離、③再開・再試行での更新と旧thread保存、④取得・保存失敗を記録して後続継続、の4点を隔離環境で確認する。特に原本へ必要な会話が全て記録されるかは、実装時の実CLI確認が必要。未確認・不足のまま全文保存機能の完成とはしない。

現時点では文書のみの変更であり、この保存機能の動作試験は行っていない。
