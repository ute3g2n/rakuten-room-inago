## U23 現行運用方針

自動不具合対応フロー全体で、review/test/readiness/release status、証拠不足、原因unknown、FAIL、rejected/changes_requested/unavailable、retry/review回数を後続処理のgateにしない。「絶対にどうしても必要」な例外は基本的にない。個別操作が実行不能なら、その操作だけ未実施として記録し、実行可能な後続stageとreportを続ける。report担当はreview所見を反映してreportを修正できる。
対象job・担当stageとreview対象version/artifactが分かる場合、担当agent/reviewerを実際に起動する。model/effort/runtime観測、session/cache状態、receipt、任意証拠の事前確認で起動を見送り、起動前に合成`unavailable`を作らない。要求したCLI/modelが使えないと事前に推測せず、利用可能なdefault設定で実起動を試みる。実起動要求後に環境が拒否した場合はその実際の失敗を記録し、独立した後続stageとreportを続ける。

以下のU05～U21節はschema・実装・判断の履歴を説明する。そこに残る`release_gate`、承認済みpredecessor、必須PASS、worker/provider準備完了、lease、外部証拠の記述は、現行の後続stage開始条件としては適用しない。`blocked`等の値は該当操作の状態を表す記録値とする。対象を特定できず誤操作になる場合はその操作だけを未実施にし、対象が確定している独立工程とreportは続ける。

## 関係と一意性

run→attempt/source/selection/draftは外部キー。offer→draft/reservation/publication/exclusionはoffer_key外部キー。publicationは公開に使ったdraft版を参照し、後の本人修正で入口本文を上書きしない。
新日次(target_date,daily)は一意。同run同offerの生成初版は一意。active reservationはoffer_key一意。publication/human_action/報告反映/選択count_event/attempt開始はidempotency keyで重複を防ぐ。誤入力訂正は原イベント参照を持ち、有効証拠集合から除外キーを再計算する。
本人の古いHTMLから実投稿申告を受けた場合は未反映のhuman_actionへ保存し、翌日日次で反映する時に、同offerの後発active予約を全て解除し、後発本文はdo_not_post_already_postedへ。本文生成件数の履歴は減らさず、現在投稿に使える件数を別に表示する。本文を削除して帳尻を合わせない。
raw証拠の期限削除は外部キーの参照キーを残してexpiredへ。復元時に有効な投稿/未解決予約を優先し、expired artifactを今ある根拠に戻さない。バックアップ後の受付記録が未補完、または回収対象の管理反映が未完了なら新選出停止。

## FC02 全工程完遂・失敗追跡の現行契約（2026-10-19）

要件正本HTML 2.50 §27.18と承認実行計画1.2のFC-R01～10/FC-A01～10を局所対応として追加する。既存MR/MAを新規承認IDへ置換しない。旧U05～U23のblocked/approval/worktree/incident resolved結合は旧仕様履歴であり、現行は次の契約を使う。

- `stage_progress=pending/running/completed`、`operation_result=succeeded/failed/not_performed`、`content_result=confirmed/unknown/partial/no_change`、`artifact_origin=agent/controller_fallback`を分離する。新規stageにblockedを返さず、raw旧履歴は改変しない。

## FC10 invocation-bound handoffと二次journal

`invocation_id`はhost/controllerが各workflow実行で正式採番する。stage handoff schemaの必須fieldであり、payload内の値はその成果を生成した実行を示す。terminal reconcilerはpathが現在実行の配下にあることだけに頼らず、payload内のIDと現在invocationを照合する。AI担当はこのfieldを創作せず、controllerは通常成果・fallback成果の双方に同じ正式IDを設定する。

failure journalは通常先`maintenance/failure-journal/events.jsonl`に加え、primary書込/path解決失敗時用の`maintenance/failure-journal-secondary/events.jsonl`を持つ。secondaryは検証済みmaintenance DB rootから個別に解決され、primary pathが失敗しても読み込み・replayを試す。両方のeventをevent IDで重複排除してDBへ冪等再生し、sink自身の失敗は具体的な安全化情報を返して元operationを止めない。

deployment resultを完了証拠にする時は、登録schema、current repair attempt、candidate内容/version、repair handoff hash、formal release recordをread-back照合する。内容が似たJSONや古い別invocation handoffは完了根拠として採用しない。2026-10-20のschema v15適用後とFC10同一job結果は、推測せず各STEP実行記録から参照する。
