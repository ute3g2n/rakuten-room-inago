## U05 management DB schema v1

- DB：`D/maintenance/state.sqlite`。日次 `D/state.sqlite` と別fileであり、初期実装/検証中にproduction DBを初期化しない。migrationは`001_initial.sql`、`application_id=0x494E474D`、`user_version=1`。管理設定は`D/maintenance/settings.json`（`schema_version=1`、`settings_version="1.0"`）。
- Table：`schema_migration`, `daily_check`, `incident`, `incident_run`, `release`, `release_required_test`, `test_ledger`, `review_result`, `deployment`, `release_gate`, `maintenance_job`, `lease`, `step_attempt`, `handoff_artifact`。
- Nullable `source_run_id`：`daily_check`, `incident_run`, `maintenance_job`, `step_attempt`, `handoff_artifact`。未生成runに架空IDを補わない。
- Status enum：`daily_check.check_status`=`normal/normal_shortfall/abnormal/unknown/incomplete`; `incident.status`=`open/in_progress/blocked/resolved/closed`; `release.state`=`frozen/withdrawn`; `release_gate.status`=`blocked/ready`; `maintenance_job.status`=`queued/running/blocked/complete/failed/cancelled`; `lease.state`=`held/released`; `step_attempt.status`=`running/interrupted/complete/failed/blocked/cancelled/handoff_accepted`; `review_result.status`=`approved/changes_requested/rejected/unavailable`; `test_ledger.status`=`PASS/FAIL/SKIP/XFAIL/ERROR/NOT_RUN/UNVERIFIED`; `deployment.status`=`pending/deployed/failed/blocked/rolled_back`。
- `source_launch_id`は一意。未解決incidentはdedupe keyごとに1件、active maintenance jobは全体1件。各更新はSQLite transaction内で確定する。
- release必須caseは`release_required_test.sequence`順でmanifestを固定し、そのSHA-256を保存。gateはmanifest一致、各最新試験PASS・同じ`result_version`、最新の独立承認、result commit/config version一致のdeploymentを再計算する。`ready`を手入力しても`start-job`はgateを再評価し、条件未達なら開始しない。
- U05追加欄：`maintenance_job.finished_at`と`terminal_reason_code`はjob終端化時に保存する。`complete`は最新gate readyと全step sequenceの最新attempt・最新独立reviewが一致する場合だけ許可する。`failed/blocked/cancelled`はsafe reason codeを要し、running attemptを同じ終端状態へ移してactive job枠を解放する。
- reviewはrelease単位と同一job内のstep単位（同一stepの全attempt通算）で最大`review_round_limit=3`件。stepを次へ進めるには前sequenceの最新attemptが完了し、同じ`result_version`への最新reviewが独立した`approved`であること。`changes_requested`後の再試行は同じstepの新attemptとして記録する。上限後は追加reviewと次attempt開始を拒否し、保留する。reviewはcomplete後だけ記録でき、handoff受理後は追加できない。handoffはactive jobとjobに紐づく現在leaseを照合する。resume上限到達後は現在leaseで`blocked`終端化し、slotを解放する。CLIは`{init,status,release-gate,start-job,finish-job}`。
- leaseはowner ID/PID/process start time・generation・状態・期限を保持。期限切れだけで奪わず、観測済みの`dead/reused`を要求する。`step_attempt`はlease key/generationを記録し、同世代のrunning attempt重複を拒否する。次sequenceの前に前sequenceの最新attemptが`complete/handoff_accepted`であることを確認する。再開はlease generationの更新ごとに数え、settingsの`job_resume_limit=3`を超えない。
- CLI：`python -m automation.inago.maintenance.cli --data-root D [--daily-database PATH] {init,status,release-gate,start-job}`。`settings.json`の未知schema/value、管理DBの未知schema/version、日次DBと同じfileを拒否する。

状態の正本はmaintenance管理SQLiteと検証済みファイル。既存日次SQLite、L02 trace、CLI元結果の正本を置き換えない。U05のmanagement DB/CLI契約は専用の隔離rootで検証済みだが、production導入は未実施。診断JSONLのfield/atomic append/quotaは後続STEPで確定する。

## U07 management DB schema v2 補足

- U05 schema v1に`002_job_manifest_ai_sessions.sql`を適用してversion 2にする。v1のCLI/state tableは履歴として保持し、production DBをこのSTEPで初期化・移行しない。
- `job_input_manifest`はjobごとに`incident_id`、`source_launch_id`、nullable `source_run_id`、`target_date`、`job_id`の完全な入力identityとdigestを一度だけ保存する。UPDATE/DELETEを拒否し、欠落・不一致・曖昧、または`source_run_id`のnullness不一致はAI session開始前にblockedとする。既存jobにmanifestを推測生成しない。
- maintenance_ai_sessionはjob/session/親AまたはB/role/thread、manifest digest、要求model/effort/service tier/Fast、role TOML digest、sandbox mode（readOnly/workspaceWrite）とnetworkAccess設定を保存する。identityと設定はimmutable。TOMLのdeveloper_instructionsをsessionへ渡すが、本文をlogへ出さない。folder-level rootsは保存・強制しない。
- `maintenance_ai_observation`はappend-onlyで、状態を`configured_unverified`/`verified`/`blocked`のいずれかにする。観測できたmodel/effort/service tierのみを保存し、要求値だけでは`verified`にしない。
- 親Aは`gpt-6.1-sol`/`xhigh`/`default`/Fast無効、親Bは`gpt-6-luna`/`max`/Fast指定を使う。親BのFastはCLI設定`service_tier="fast"`と`features.fast_mode=true`、protocol tier `priority`で要求する。モデル・effort・tier・Fast capabilityが未対応ならfallbackせず起動を拒否する。
- 調査/review roleはreadOnly mode、親Bの実装/試験roleは専用managed worktree cwdでworkspaceWrite modeを使う。per-folder rootsはCLIで強制せず、allowed_outputsはroleの返却/所有契約として扱う。管理DB上のrunning step attemptがjob/source runと一致すること、出力rootが`attempts/<job_id>/<attempt_id>`、worktreeが`worktrees/<job_id>`であることをhostが検証する。configured rootからjob/attempt directoryまでの全componentにreparse point（symlink/junction等）がなく、resolve後もroot配下であることを計画時・turn前・保存時に確認する。AI返却JSONはDraft 2020-12 schemaとmanifest 5項目identityを検証し、`maintenance-ai-response-v1` envelope（identity、attempt_id、owner、role config digest、allowed_outputs、thread/turn、観測状態、response）として当該attempt output rootへ原子的に保存する。allowed_outputsのWindows無効文字・予約名・末尾ドット/空白・衝突は拒否する。保存後のpath/hashをcontrollerへ返す。Bのdiffはhandoff/release前に宣言済みownerと照合し、owner外変更を未承認とする。sandbox全面解除はしない。

U07は隔離pytestでmigration、manifest/session、基本sandbox modeとper-folder root allowlistを要求しないapp-server起動、turn responseのschema/identity/owner/allowed_outputs検証とattempt output保存を確認する。実モデルのLC01/LC02接続はU18まで行わない。本人決定と実行結果は実行計画M §14およびU07の非公開証拠に記録する。

## 関係と一意性

run→attempt/source/selection/draftは外部キー。offer→draft/reservation/publication/exclusionはoffer_key外部キー。publicationは公開に使ったdraft版を参照し、後の本人修正で入口本文を上書きしない。
新日次(target_date,daily)は一意。同run同offerの生成初版は一意。active reservationはoffer_key一意。publication/human_action/報告反映/選択count_event/attempt開始はidempotency keyで重複を防ぐ。誤入力訂正は原イベント参照を持ち、有効証拠集合から除外キーを再計算する。
本人の古いHTMLから実投稿申告を受けた場合は未反映のhuman_actionへ保存し、翌日日次で反映する時に、同offerの後発active予約を全て解除し、後発本文はdo_not_post_already_postedへ。本文生成件数の履歴は減らさず、現在投稿に使える件数を別に表示する。本文を削除して帳尻を合わせない。
raw証拠の期限削除は外部キーの参照キーを残してexpiredへ。復元時に有効な投稿/未解決予約を優先し、expired artifactを今ある根拠に戻さない。バックアップ後の受付記録が未補完、または回収対象の管理反映が未完了なら新選出停止。
型例のIR-016/AT-016と、停止/競合/見送り後の本人投稿はAT-S14/19/20/25/26/29で実装テストする。

## 版1.4：AI-Oとnative子実行・語句選択・ログの補足

AI-Oは13:00のスケジューラ→Python制御から起動する日次オーケストレータで、常時の本人対話役ではない。root_job_id:string!、parent_job_id:string?、native_agent_ref:string?、実モデル・推論・認証種類・指示書・入力参照・回答形式・時刻・採用状態を記録する。rootのparentはnull、専門役は実在する親とnative子参照が必要。六専門役を独立CLIで順次起動した結果をnative子委譲として受理しない。日次外のAI-Oは本人の明示依頼時のみ。

語句選択は観測Top20内の重複グループから最大5を均等抽選し、各グループ内の原表現も均等抽選する。グループ構成・選択word_id・raw・source_rank・seed・候補実数・除外理由・settings_versionを保存する。3候補しかなければ3語を使い、商品不足は他テーマで補う。relatedの検索queryにraw以外の語を付加せず、ID不一致・新語追加・順位改変を処理エラーにする。本人指定のtheme_fallbackは別契約として採用テーマ参照を検査し、word_idを創作しない。初期3テーマ各5商品。テーマごとに保存した語順で必要分だけ検索し、不足時にテーマ単独を1回検索してから次テーマへ進む。初期3テーマ後に15件未達なら未試行テーマを追加する。検索回数は上限なしで、15件到達・有限候補枯渇・有限retry後の継続不能障害・明示停止等で終了する。

任意部品へデバッグ・トレース機能を恒久的に追加できる。大きい詳細ログは90日、必要なコンパクトな運用履歴は運用中保持という既存の区分を適用する。秘密値・不要な個人情報を公開ログへ転記せず、ログを状態正本や完成の証拠そのものへ置き換えない。

業務上のAI入力照合input_hashと実行artifactの既存契約は残す。要件文書・計画・引渡し成果物のハッシュ生成・一覧・一致判定は追加しない。旧フィールドの保存履歴と新運用の必須項目を版で区別する。文書改訂でDB移行は実行しない。

日次検索のcheckpointは初期/追加テーマの処理順、テーマ別の目標/確定件数、選択word_idの使用順・使用済み集合、テーマ単独の実施済み印、再利用するattempt参照を版付きで保存する。実装列名は委任するが、同run再開で候補を引き直す、実施済みの単独検索を繰り返す、失敗商品の回数を戻す処理は認めない。

## 版1.9：商品詳細の行単位失敗と検索全体の境界（IR-010/013/019、AT-S04）

ROOMの商品紹介投稿から商品ページを開いて商品IDを特定できない場合は、その受理投稿行だけの詳細解決失敗として数える。先頭50投稿の範囲で失敗が10件以下なら、失敗行は候補から除外するが検索全体は`observed`として扱い、残る受理済み行の処理と次の検索を続ける。失敗行も受理した先頭50件の母数に残し、51件目以降で穴埋めしない。失敗が11件以上なら検索を`partial`として既存の日次再試行・停止制御へ渡す。

## 版2.6：実UI見出しselectorの意味分類（R05）

`related-widget-v3`は対象widget内にある可視の`h2`/`h3`/`[role="heading"]`を走査し、「関連トピック」「関連キーワード/検索/クエリ」および許可済み英語同義表現を`related_topics`/`related_keywords`へ分類する。traceへ記録するのはselector version、種別、件数、更新世代、結果enumだけ。見出し文字列そのものを保存せず、v2 selectorを用いた既存traceは後方互換で受け入れる。N08bでsemantic heading aliasを隔離fixture検証し、実UI接続L01の再確認は独立nodeとする。

## 版2.7：title containerとアクセシブルラベル（R05）

`related-widget-v4`は可視`h1`～`h6`/`[role="heading"]`と、widget内のtitle/heading class、widgetの`aria-label`、可視`aria-labelledby`を候補にする。候補labelの日本語/英語の意味分類が一意な場合だけ`related_keywords`または`related_topics`とし、候補が矛盾/未認識なら`unknown`を維持する。raw見出し、語句、URL、DOMはtraceへ保存しない。N08cはclass title alias成功と未知headingのcontract mismatchを隔離fixtureで確認する。L01の実UI適合は独立接続nodeで別途確認する。
