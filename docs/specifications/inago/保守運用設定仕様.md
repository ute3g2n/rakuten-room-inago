# 保守運用設定仕様

仕様版：1.5（2026-10-19 JST）
要件正本：イナゴスキル要件定義書HTML 2.50 §27.17～27.18、AT-MAINT-01、実行計画M §7。
状態：運用値、U05～U09/U15/U18/U21/U23の管理DB/launcher/dispatch/verification契約、U17 MN04 diagnostic JSONL schema v1/retention、historical job再開契約、および後続処理を状態で止めない方針を記載する。AI sessionはreadOnly/workspaceWriteとnetworkAccess=falseを使い、per-folder sandbox rootsは要求しない。review、試験、readiness、release gate、原因確度、証拠不足は記録値であり、後続stageを止めない。出力や根拠に欠けがあればそのまま未確認として渡す。

本仕様は日次イナゴ処理とは別の保守・障害対応基盤の初期運用値を定める。値を採用するのは計画されたmaintenance処理だけで、既存日次のtimeout/retry/保持値へ一括適用しない。

## 共通方針：後続stageを状態で止めない

自動不具合対応フロー全体で、前工程の状態による後続処理へのgateを設けない。review/test/readiness/release status、原因確度がunknownであること、証拠不足、FAIL、rejected/changes_requested/unavailable、retry/review回数は記録値であり、調査、計画、実装、試験、review、反映、報告の開始条件にしない。「絶対にどうしても必要」なgateは原則として存在しないものとして扱う。失敗・欠測・未確認は成功に書き換えず、そのまま次担当と最終報告へ渡す。ある操作を実行できない場合はその操作だけ未実施として記録し、他の後続工程と報告を続ける。対象を一意に選べない場合も、その操作を保留する理由だけを記録して、別の実行可能な工程を止めない。個別操作の実行不能をworkflow全体のblockedへ拡大しない。既存のU05～U21節にある承認・readiness・release gate条件は当時の実装・判断履歴であり、現行の後続処理gateとしては適用しない。

## ログと証拠の保持

| 対象 | 確定値 | 適用規則 |
|---|---:|---|
| maintenance JSONL | 90日 | maintenance専用schema/保存先。既存L01～L05・M01/M02等の保持を変更しない。 |
| JSONL 1ファイル | 4 MiB | 上限前にrotateし、ファイル単位で期限を管理する。 |
| JSONL ファイル数 | 上限なし | 同一maintenance IDは1ファイル4 MiBでrotateし、ファイル単位で90日保持する。旧設定の`diagnostic_log_max_files_per_day=20`は互換読込のみ行い、無視する。 |
| 採取証拠のコピー | 原本期限または採取後90日の早い方 | 元期限、採取時刻、取得不能・失効理由を索引へ保持する。既存原本の保持規則は変更しない。 |
| 公開可能な伏字済み計画・報告・レビュー | Git履歴に保持 | 秘密、認証値、商品/投稿本文、個人情報を含めない。 |

ログにはstage/status、許可済みID、件数、safe error code/class、相関ID、版、参照だけを記録する。prompt、AI応答本文、URL、query、DOM、認証情報、任意自由文を記録しない。書込失敗・ファイルサイズ超過・保全不能は成功へ読み替えない。

U17 MN04 diagnostic JSONLは`automation/inago/schemas/maintenance-diagnostic-event.schema.json`でevent schema v1を検証し、`D/maintenance/logs/<target_date>/<maintenance_id>.jsonl`へ保存する。1 event 16 KiB、1 file 4 MiB、ファイル数上限なし、保持90日。file上限前に`.part-NNNN.jsonl`（必要に応じ4桁超）へrotateする。記録できなかったeventは成功扱いせず、その記録操作の失敗を残して、可能な後続stageとreportを続ける。書込はtemporary stageへのflush/fsync後にatomic replaceする。IDをまだ取得できない起動前エラーはnullのsource IDとsafeなcode/classで記録し、架空run/job/incident IDを作らない。

MN04のsettingsは`automation/inago/schemas/maintenance-settings.schema.json`（schema version 1、settings version 1.5）に固定し、90日/4 MiBを含む保守専用値を日次側の保持/timeoutへ流用しない。旧1.0～1.4設定は読取時に現行値へ正規化し、旧`job_resume_limit`、`review_round_limit`、1日20 file項目は互換読込して無視する。再開回数・review巡回回数に上限を設けない。新規設定にファイル数上限もない。古い保守log stageと中断した証拠bundle stageだけを回収し、元の日次ログ・証拠原本は削除しない。MN05 app-server transport logは別の出力として管理する。

## 正常日から復旧まで

日次のCLI最終結果、工程trace、export、preservation/end backupを照合してからcheckを確定する。正常または根拠のある正常不足ならcheckのみで終了し、異常/未知だけをincident工程へ渡す。日次全体の17:45/18:00終了時刻を再導入しない。

基盤releaseのレビュー・テスト・実接続・Git追跡先・実起動設定の各状態は観測値として記録し、後続のhistorical job処理開始条件にしない。実行できないrelease操作だけを未実施として記録し、対象jobの調査・修正・reportを続ける。source runが存在しない場合 `source_run_id=null` を使い、元の日次結果を変更しない。

## U08の日次launcher・最終結果通知

日次task XMLと`run.ps1 daily`は`automation.inago.maintenance.daily_launcher`を入口とする予定差分である。launcherはmanagement DBの起動記録をcommitしてから日次CLIを子processとして開始し、子PIDを記録して完了までwaitする。日次CLIがexport、終了保全、共通trace、L01最終記録まで返却した後にdaily_checkと最終通知を確定する。親launcher/child/ownerの終了確認前はworkerを起動しない。Scheduler `ExecutionTimeLimit=PT0S`を維持し、全体期限を設けず、既存の個別有限timeoutを使う。

## U12 調査出力・review・checkの実装境界

U12のcontroller stageは、合成確認でnormal checkをdaily_checkへ記録し、異常/unknown/外部待ち/契約違反を区別して保存する。調査attemptのfacts.json、9章investigation.md、result.jsonはattempt専用rootに保存し、path/hash/版を記録する。調査担当がinvestigation.md本文を作成・修正し、controllerは本文をそのまま保存する。path整合性は書込先を保つ目的に限って使う。review status/findingsは監査・改善情報として記録し、handoff/後続stageの条件にしない。確認できない章や値は未確認と記録して成果を保存し、後続stageへ渡す。
## U21.05.01 report publication・終端化・再開同期（2026-10-19）

### FC03 fallback journalと設定版1.6

maintenanceのoperation診断は通常JSONLへbest-effortで書き、失敗時もstage処理を中断しない。fallbackは`D/maintenance/failure-journal/events.jsonl`へ独立追記し、発生時刻、相関/対象ID、operation、phase、実行版、例外class連鎖、コード位置、参照を残す。journal自体の保存ができない場合はsafeなstderr markerだけを最後の採取先とし、その間の詳細は後の復帰時に不明として扱う。起動時にjournalを管理DBへ再照合し、beginのみ残った操作には中断観測を追記する。settings version 1.6は固定journal filenameを持ち、旧1.0～1.5は読取時に新fieldを補って1.6へ正規化する。切替え可能なenable flagは設けず、通常処理を停止するログreceipt gateを作らない。


### FC04 調査・計画・実装の成果引継ぎ

調査担当の実行失敗や空・不正応答、証拠不足でも、確認できた事実と調べた範囲、不明な点、次の確認を含む9章の調査成果を保存して計画担当を実起動する。controllerが代替文書を作った場合は担当AIの成果と区別する。計画担当は原因修正または次回の原因特定に役立つ記録追加の具体策を出し、両方ができない場合も変更しなかった理由を平易なHTMLにする手順を残す。調査や計画の失敗を将来stageのblocked結果にせず、必須対象が識別できる限り後続を続ける。修正担当は固定されたリポジトリroot内で作業し、別checkout/worktreeを作らない。

### FC05 終端と再開

maintenanceの設定やrole状態は試験・review・releaseの開始gateではない。各操作の未実施理由、結果、参照を保存し、利用可能な後続工程へ引き渡す。workflow完遂は同一jobの成果と公開版および終端read-backで確かめる。incident resolutionは別項目とし、原因または業務回復が不明ならunknownを維持する。

### FC06 report公開の設定契約
report本文の公開状態、reviewの承認状態、workflow終端、incident解決を独立して保持する。公開処理は別worktreeを作らず、remoteを基準に一時Git indexでreport HTMLのみをcommit候補にする。remoteへの反映を読み戻した後に、同一jobのpublication sidecarと終端状態を保存する。identity/target不一致、remote push、sidecar保存失敗は具体的reason codeを保持し、相関付きfailure journalと工程handoffへ記録する。report publication stageはblockedを返さずunknown/failedで終端照合へ進む。
