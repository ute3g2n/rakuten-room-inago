# 保守運用設定仕様

仕様版：1.0（2026-10-17 JST）
要件正本：イナゴスキル要件定義書HTML 2.25 §27.17、AT-MAINT-01、実行計画M §7。
状態：運用値、U05管理DB schema v1、U07 schema v2とAI session設定、U08 schema v3の日次launcher契約、U09 schema v4のwatchdog確認queueを記載する。AI sessionはreadOnly/workspaceWriteとnetworkAccess=falseを使い、per-folder sandbox rootsは要求しない。A出力の保存とBの差分所有はhost/controller側で検証する。実モデル接続、production migration、Scheduler登録、MN04のfull diagnostic JSONL/quotaは後続STEPで確認する。

本仕様は日次イナゴ処理とは別の保守・障害対応基盤の初期運用値を定める。値を採用するのは計画されたmaintenance処理だけで、既存日次のtimeout/retry/保持値へ一括適用しない。

## 実行と排他

| 設定 | 確定値 | 適用規則 |
|---|---:|---|
| 対象タイムゾーン | `Asia/Tokyo` | `target_date`はJST暦日。対象日、実行/採取/受付/作成/反映時刻を分離する。 |
| 日次開始 | 13:00 JST | 既存の日次開始条件を維持する。 |
| 日次とmaintenanceの全体終了期限 | なし | 17:45/18:00等のrun-wide deadlineを設定しない。 |
| Windows Task Schedulerの日次 `ExecutionTimeLimit` | `PT0S` | 登録済み値をテンプレートと照合する。実行中のtaskは変更せず保留する。 |
| 同時コード修正案件 | 1件 | 追加案件は状態を保持して待機する。 |
| lease heartbeat | 30秒 | 所有者、lease、worker状態を永続管理する。PIDのみで解除しない。 |
| watchdog確認間隔 | 60秒 | 起動未確認・通知欠落・途中終了を補完する。所有者確認前にprocessを停止しない。 |
| 1 AI jobのtimeout | 20分 | 個別jobの上限。遅延応答をtimeout後に採用しない。 |
| 個別request/job取消確認 | 60秒 | 対象IDを確認する。確認できなければ当該runの後続を止め、状態を記録する。 |
| 通信一時失敗retry | 初回に加え最大2回 | retry回数は再試行数。`Retry-After`およびより厳しい既存上限を優先する。恒久失敗はretryしない。 |
| 各レビューの差し戻し | 最大3巡 | 3巡後も未解決なら保留し、指摘と再開条件を保持する。 |
| 1案件の再開 | 初回開始後、最大3回 | 既存のincident/check/attemptを再利用し、新規重複案件へ置き換えない。 |
| 次の日次との優先 | 次の日次を優先 | 調査・隔離試験は継続できるが、本番反映は日次/API切替との排他が成立するまで待機する。 |

## ログと証拠の保持

| 対象 | 確定値 | 適用規則 |
|---|---:|---|
| maintenance JSONL | 90日 | maintenance専用schema/保存先。既存L01～L05・M01/M02等の保持を変更しない。 |
| JSONL 1ファイル | 4 MiB | 上限前にrotateし、ファイル単位で期限を管理する。 |
| JSONL 1日あたり | 20ファイル | 到達後に監査必須eventを書けない場合、記録欠落を隠して進めず、反映・gateを保留する。 |
| 採取証拠のコピー | 原本に期限があればその期限まで。それ以外は採取後90日 | 元期限、採取時刻、取得不能・失効理由を索引へ保持する。既存原本の保持規則は変更しない。 |
| 公開可能な伏字済み計画・報告・レビュー | Git履歴に保持 | 秘密、認証値、商品/投稿本文、個人情報を含めない。 |

ログにはstage/status、許可済みID、件数、safe error code/class、相関ID、版、参照だけを記録する。prompt、AI応答本文、URL、query、DOM、認証情報、任意自由文を記録しない。書込失敗・quota到達・保全不能は成功へ読み替えない。

## 正常日から復旧まで

日次のCLI最終結果、工程trace、export、preservation/end backupを照合してからcheckを確定する。正常または根拠のある正常不足ならcheckのみで終了し、異常/未知だけをincident工程へ渡す。日次全体の17:45/18:00終了時刻を再導入しない。

基盤releaseは要件・構成・レビュー・凍結必須テスト・必要な実接続・Git追跡先・実起動設定の一致がそろうまで `ready` にしない。10/17の遡及案件はready後に限る。source runが存在しない場合 `source_run_id=null` を使い、元の日次結果を変更しない。

## U05で確定した保存・実行契約

| 項目 | 確定値 |
|---|---|
| 管理DB | `D/maintenance/state.sqlite`、SQLite `schema_version=1`。業務日次DB `D/state.sqlite` と分離し、同一パス/同一fileを拒否する。 |
| 管理DB migration | `automation/inago/maintenance/sql/001_initial.sql`。14 tableを作成し、既知外のschema/versionは拒否する。 |
| 保守設定 | `D/maintenance/settings.json`、`schema_version=1`、`settings_version="1.0"`。固定された承認初期値以外や未知fieldを拒否し、秘密値を設定schemaへ含めない。 |
| CLI | `python -m automation.inago.maintenance.cli --data-root D [--daily-database PATH] {init,status,watchdog,release-gate,start-job,finish-job}`。`finish-job`は現在lease tokenを要し、`complete/failed/blocked/cancelled`を終端化する。`--daily-database`省略時は`D/state.sqlite`を隔離比較先にする。`worker --once`は後続実装まで未提供。登録scriptはworker commandと`worker --help`の`--once` optionが使えることを確認してからtask登録へ進む。 |
| 起動時状態 | `init`は管理DBと設定を初期化する。その他のcommandは設定と既知schemaを検査してから開く。 |
| 同時修正 | `queued/running`のmaintenance jobは部分一意indexで全体1件に制限する。 |
| 再開・承認 | stepは連番で、前stepの最新attemptが`complete/handoff_accepted`かつそのresult versionに対する最新独立reviewが`approved`であること。`changes_requested`後は同じstepの新attemptを開始できる。同一lease generationのrunning attemptを二重開始しない。job単位の世代更新回数は設定の`job_resume_limit=3`以下。上限到達後は現在leaseで`blocked`終端化できる。handoff再開は現在・最新attemptとapproval/hash/leaseを同一transaction内で確認してから状態更新し、検証失敗で状態を変えない。accepted handoffの再試行は冪等とし、二重記録しない。handoffはjobに紐づく現在leaseでのみ受理し、受理後のreview追加を拒否する。 |
| review巡 | `review_round_limit=3`。release単位、および同一job内のstep単位（stepの全attemptを通算）に数える。上限後の追加reviewと差し戻し後の次attempt開始を拒否し、保留する。 |
| job終端化 | `finish-job`の`complete`は最新release gateと全step最新attemptの独立承認を再確認する。`failed/blocked/cancelled`はsafe `reason_code`が必要で、稼働中attemptも同じ終端状態へ移す。終端状態でactive job枠を解放する。 |
| release gate | 凍結した必須case manifest/hash、全caseの最新PASSと同じresult version、最新独立review、result commit/configに合うdeploymentを毎回再計算する。全条件成立前の修正開始を拒否する。 |

具体的なtable名・field・status enumは[要件データ辞書](要件データ辞書.md)に記載する。初期実装と試験は専用の隔離領域だけで行い、productionの管理DBは初期化していない。U05の実装は本番運用、モデル設定の実適用、日次不具合の調査・修正が済んだことを意味しない。

## U08の日次launcher・最終結果通知

日次task XMLと`run.ps1 daily`は`automation.inago.maintenance.daily_launcher`を入口とする予定差分である。launcherはmanagement DBの起動記録をcommitしてから日次CLIを子processとして開始し、子PIDを記録して完了までwaitする。日次CLIがexport、終了保全、共通trace、L01最終記録まで返却した後にdaily_checkと最終通知を確定する。親launcher/child/ownerの終了確認前はworkerを起動しない。Scheduler `ExecutionTimeLimit=PT0S`を維持し、全体期限を設けず、既存の個別有限timeoutを使う。

| 項目 | U08で確定した契約 |
|---|---|
| 管理DB schema | 現行コードschema v4。`001_initial.sql`～`004_watchdog_confirmation_queue.sql`を順次適用する。隔離DBでmigration/完了記録/queueを検証し、production DBは初期化・移行していない。 |
| 自動migration | launcherはproduction管理DBを自動migrationしない。schema v4の既存DBがない、またはschema確認に失敗した場合はdaily childを起動せずblockedで停止する。 |
| 起動記録 | `daily_launch`へ`source_launch_id`、JST対象日、owner PID/開始時刻をrunningで保存する。child PID/開始時刻は起動直後に一度だけ記録する。旧rowの開始時刻NULLや観測不能は所有確認不明として扱う。開始記録が保存できない場合は日次を起動しない。 |
| 完了通知 | 日次CLIの終了後、run ID（未生成ならnull）、整数の終了コード、必須のoverall/daily status、safe reason/phase/error class、failed checks、trace statusを保存する。正常・不足・未実施の要約には対象日一致を必須とし、正常/不足にはrun IDも必須とする。失敗statusには成功overall statusを組み合わせない。要約の型/status/終了コードが矛盾する場合や、成功コードにparse可能な結果がない場合は契約エラーとしてexit 4にし、成功コードを返さない。非文字列trace statusは`not_written`とする。`daily_launch`終端化と`daily_check`を同一transactionで確定し、終端行をimmutableにする。 |
| 出力制限 | 許可済みID/列挙値/code/classだけをsummary/stderrへ出す。raw stdout/stderr、自由文、秘密、path、下書き数は管理DBへ保存しない。 |
| 通知保存失敗 | 有効な日次結果の保存だけに失敗した場合、起動行をrunningのまま保持してU09 watchdogへ渡し、daily CLIの本来のexit codeを維持する。子結果自体が不正/矛盾している場合は契約エラーexit 4とする。 |
| watchdog確認 | C12/C13で扱う未起動/途中終了はtask/対象日で安定したoccurrence keyとsource launch単位で`watchdog_queue`へ一意に記録する。`watchdog_cursor`は照合済み日付を後退させず、新規予定日・当日・未解決queue日・running launch日を継続確認する。未解決queue日は現Scheduler開始境界より前でも再照合する。child PID未記録、process開始時刻不明、running/unknown processは保留し、別processをkillしない。historyが使えない場合もtask schedule境界から予定時刻を判定する。 |
| task XML/登録 | watchdogは毎分起動するtask XML、workerはtriggerなし/明示起動のtask XMLとして用意する。登録scriptは既定でrender-only。実登録前にworker CLI commandと`--once` option、および全task名の衝突を確認し、登録失敗時は今回追加分のみrollbackする。現在CLIにworker commandがないため登録経路はfail-closed。U09では登録せず、worker implementation・production DB migration・Scheduler登録はU21 gate後。 |
| 実行状態 | U08 daily XMLは予定差分。U09 watchdog/worker XMLと登録scriptを追加したが、Schedulerへ登録していない。production DB migrationと実日次接続はU21の導入ゲート後に行う。 |

この契約の型・enum・summary schemaは[要件データ辞書](要件データ辞書.md)と[AT-TRACE-01](AT-TRACE-01_共通トレース契約.md)、実装後の受入は[AT-MAINT-01](AT-MAINT-01_保守対応要件受入契約.md)とM §14へ同期する。C32の基本run-null summaryはU08で観測し、C32全体の計画追加ログ契約はU13で検証する。

運用値を変更する必要が生じた場合は、根拠・影響・要件/辞書/trace/受入への反映を記録し、独立レビューを通す。MN04のfull maintenance JSONL schema/path/quotaとproduction migrationは後続STEPで確定する。

## U12 調査出力・review・checkの実装境界

U12のcontroller stageは、合成確認でnormal checkを`daily_check`へ記録し、異常/unknown/外部待ち/契約違反を混同しない。調査attemptの`facts.json`、9章`investigation.md`、`result.json`はattempt専用rootに保存し、path/hash/版をStoreへ結ぶ。POSIXではdirfd相対`O_NOFOLLOW`、Windowsではhandle-relative `NtCreateFile`/`OBJ_DONT_REPARSE`とfinal-path照合を使ってlink/reparse escapeを拒否する。blocked調査も成果3点を保存する。artifact書込み失敗時は開いたstream/descriptor/handleを閉じてからpartial fileをroot-relativeに削除し、削除失敗は元の書込例外へ付記する。fresh reviewerは担当IDと実行IDの双方を調査担当から分離し、以前のreview execution IDを再利用せず、Store由来のreview roundとleaseを確認した同一版のapprovalだけをhandoff可能とする。handoff再開時もStore transaction内でcurrent/latest・approval・版・hash・leaseを照合し、検証前にjob/attemptを変更しない。accepted handoffのretryは冪等に同じ結果を返す。

U12は隔離Storeと合成fixtureによる構造確認であり、指定Sol/xhighの実app-server接続、実観測値、production DB、Scheduler登録、実障害入力を意味しない。model/effort/tierのruntime接続はU18、production gateはU21の確認後に限る。CLIのfolder-level ACLは要求しない。attempt/output rootのpath integrity検査とschema/identity/owner/hash検証は維持する。
