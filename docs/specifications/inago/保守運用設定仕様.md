# 保守運用設定仕様

仕様版：1.4（2026-10-19 JST）
要件正本：イナゴスキル要件定義書HTML 2.42 §27.17、AT-MAINT-01、実行計画M §7。
状態：運用値、U05～U09/U15/U18の管理DB/launcher/dispatch/verification契約、U17 MN04 diagnostic JSONL schema v1/retention、およびU21 daily result observationのrouting契約を記載する。AI sessionはreadOnly/workspaceWriteとnetworkAccess=falseを使い、per-folder sandbox rootsは要求しない。A出力の保存とBの差分所有はhost/controller側で検証する。U18で実モデル接続と隔離migrationを確認したが、production migration、Scheduler登録はU21 gateまで行わない。

本仕様は日次イナゴ処理とは別の保守・障害対応基盤の初期運用値を定める。値を採用するのは計画されたmaintenance処理だけで、既存日次のtimeout/retry/保持値へ一括適用しない。

## 実行と排他

| 設定 | 確定値 | 適用規則 |
|---|---:|---|
| 対象タイムゾーン | `Asia/Tokyo` | `target_date`はJST暦日。対象日、実行/採取/受付/作成/反映時刻を分離する。 |
| 日次開始 | 13:00 JST | 既存の日次開始条件を維持する。 |

| Windows Task Schedulerの日次 `ExecutionTimeLimit` | `PT0S` | 登録済み値をテンプレートと照合する。実行中のtaskは変更せず保留する。 |

| lease heartbeat | 30秒 | 所有者、lease、worker状態を永続管理する。PIDのみで解除しない。 |
| watchdog確認間隔 | 60秒 | 起動未確認・通知欠落・途中終了を補完する。所有者確認前にprocessを停止しない。 |
| 1 AI jobのtimeout | 20分 | 個別jobの上限。遅延応答をtimeout後に採用しない。 |

| 各レビューの差し戻し | 最大5巡 | 5巡後も未解決なら保留し、指摘と再開条件を保持する。上限は同一stepの全attemptで通算する。 |
| 1案件の再開 | 回数上限なし | `resume_count`は監査・状況把握のために記録するが、この数を理由に再開を拒否しない。lease、job状態、release gate、step承認などの成立条件は引き続き確認する。 |
| 次の日次との優先 | 次の日次を優先 | 調査・隔離試験は継続できるが、本番反映は日次/API切替との排他が成立するまで待機する。 |

## ログと証拠の保持

| 対象 | 確定値 | 適用規則 |
|---|---:|---|
| maintenance JSONL | 90日 | maintenance専用schema/保存先。既存L01～L05・M01/M02等の保持を変更しない。 |
| JSONL 1ファイル | 4 MiB | 上限前にrotateし、ファイル単位で期限を管理する。 |
| JSONL ファイル数 | 上限なし | 同一maintenance IDは1ファイル4 MiBでrotateし、ファイル単位で90日保持する。旧設定の`diagnostic_log_max_files_per_day=20`は互換読込のみ行い、無視する。 |
| 採取証拠のコピー | 原本期限または採取後90日の早い方 | 元期限、採取時刻、取得不能・失効理由を索引へ保持する。既存原本の保持規則は変更しない。 |
| 公開可能な伏字済み計画・報告・レビュー | Git履歴に保持 | 秘密、認証値、商品/投稿本文、個人情報を含めない。 |

ログにはstage/status、許可済みID、件数、safe error code/class、相関ID、版、参照だけを記録する。prompt、AI応答本文、URL、query、DOM、認証情報、任意自由文を記録しない。書込失敗・ファイルサイズ超過・保全不能は成功へ読み替えない。

U17 MN04 diagnostic JSONLは`automation/inago/schemas/maintenance-diagnostic-event.schema.json`でevent schema v1を検証し、`D/maintenance/logs/<target_date>/<maintenance_id>.jsonl`へ保存する。1 event 16 KiB、1 file 4 MiB、ファイル数上限なし、保持90日。file上限前に`.part-NNNN.jsonl`（必要に応じ4桁超）へrotateし、監査必須eventを保存できない場合はstage/releaseを成功扱いしない。書込はtemporary stageへのflush/fsync後にatomic replaceする。IDをまだ取得できない起動前エラーはnullのsource IDとsafeなcode/classで記録し、架空run/job/incident IDを作らない。

MN04のsettingsは`automation/inago/schemas/maintenance-settings.schema.json`（schema version 1、settings version 1.3）に固定し、90日/4 MiBを含む保守専用値を日次側の保持/timeoutへ流用しない。旧1.0/1.1/1.2設定は読取時に現行値（review 5、再開回数上限なし）へ正規化する。旧`job_resume_limit`は許可された旧版でのみ互換読込し、値にかかわらず実行時には無視する。新規設定にファイル数上限はなく、旧設定の1日20 file項目は互換読込して無視する。古い保守log stageと中断した証拠bundle stageだけを回収し、元の日次ログ・証拠原本は削除しない。MN05 app-server transport logは別の出力として管理し、MN04の保持設定を実装済みとは読み替えない。

## 正常日から復旧まで

日次のCLI最終結果、工程trace、export、preservation/end backupを照合してからcheckを確定する。正常または根拠のある正常不足ならcheckのみで終了し、異常/未知だけをincident工程へ渡す。日次全体の17:45/18:00終了時刻を再導入しない。

基盤releaseは要件・構成・レビュー・凍結必須テスト・必要な実接続・Git追跡先・実起動設定の一致がそろうまで `ready` にしない。10/17の遡及案件はready後に限る。source runが存在しない場合 `source_run_id=null` を使い、元の日次結果を変更しない。

## U08の日次launcher・最終結果通知

日次task XMLと`run.ps1 daily`は`automation.inago.maintenance.daily_launcher`を入口とする予定差分である。launcherはmanagement DBの起動記録をcommitしてから日次CLIを子processとして開始し、子PIDを記録して完了までwaitする。日次CLIがexport、終了保全、共通trace、L01最終記録まで返却した後にdaily_checkと最終通知を確定する。親launcher/child/ownerの終了確認前はworkerを起動しない。Scheduler `ExecutionTimeLimit=PT0S`を維持し、全体期限を設けず、既存の個別有限timeoutを使う。

## U12 調査出力・review・checkの実装境界

U12のcontroller stageは、合成確認でnormal checkを`daily_check`へ記録し、異常/unknown/外部待ち/契約違反を混同しない。調査attemptの`facts.json`、9章`investigation.md`、`result.json`はattempt専用rootに保存し、path/hash/版をStoreへ結ぶ。POSIXではdirfd相対`O_NOFOLLOW`、Windowsではhandle-relative `NtCreateFile`/`OBJ_DONT_REPARSE`とfinal-path照合を使ってlink/reparse escapeを拒否する。blocked調査も成果3点を保存する。artifact書込み失敗時は開いたstream/descriptor/handleを閉じてからpartial fileをroot-relativeに削除し、削除失敗は元の書込例外へ付記する。fresh reviewerは担当IDと実行IDの双方を調査担当から分離し、以前のreview execution IDを再利用せず、Store由来のreview roundとleaseを確認した同一版のapprovalだけをhandoff可能とする。handoff再開時もStore transaction内でcurrent/latest・approval・版・hash・leaseを照合し、検証前にjob/attemptを変更しない。accepted handoffのretryは冪等に同じ結果を返す。

U12は隔離Storeと合成fixtureによる構造確認であり、指定Sol/xhighの実app-server接続、実観測値、production DB、Scheduler登録、実障害入力を意味しない。model/effort/tierのruntime接続はU18、production gateはU21の確認後に限る。CLIのfolder-level ACLは要求しない。attempt/output rootのpath integrity検査とschema/identity/owner/hash検証は維持する。

## U21.05.01 report publication・終端化・再開同期（2026-10-19）

production workflow/providerには承認済みreportの公開、公開結果artifactの保存、job/incidentの終端化、完了済みjobからのreport-only復旧を接続した。公開artifactはreport-publication.jsonで、report path/hash、approved result identity/version/hash、expected target commit、source code commit、publication commit/base、remote/branch、JST観測時刻を保持する。HTML本文や認証情報は保存しない。

report publicationはmanaged detached worktreeと共有排他制御を使い、commit scopeをreport HTML一ファイルに限定する。push後にartifact保存が失敗したケースはremoteを再照合して同じpublicationを記録する。artifact保存後、job completeとincident status更新を同一transactionで確定する。job complete後にqueue再開が必要な場合、report/publicationの照合だけを行い、前段のAI・修正・deployment stageを再実行しない。ローカル合成DB/Git fixtureによる確認済みであり、本番DB migration、Scheduler登録、worker/watchdog起動は導入gateまで保留する。

テストコードの独立レビューは行わず、デバッグ時にテスト不具合が判明した場合のみ必要箇所を直す。製品コードと仕様は独立レビュー対象とする。
